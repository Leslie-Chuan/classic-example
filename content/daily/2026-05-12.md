## 今日主题

System Prompt（系统提示词）是定义AI角色、能力和行为边界的"底层指令"。今天你将学习如何设计一个专业的System Prompt，让AI从一个"通用助手"转变为"具备你团队编码规范的资深前端Reviewer"。

与User Prompt不同，System Prompt具有以下特点：
- **持久性**：贯穿整个对话，影响每一次回复
- **权重高**：模型会优先遵循System Prompt中的约束
- **角色锚定**：决定AI的"身份"和"立场"

---

## 核心概念（15分钟）

### 1. System Prompt 的三层结构

一个高效的System Prompt通常包含三个层次：

```
┌─────────────────────────────────────────┐
│  L1：角色定义（Who）                      │
│  "你是一位有8年经验的前端技术负责人..."    │
├─────────────────────────────────────────┤
│  L2：能力边界（What）                     │
│  "你擅长React/TypeScript性能优化、         │
│   代码审查、架构设计..."                  │
├─────────────────────────────────────────┤
│  L3：行为规范（How）                      │
│  "审查时请按以下格式输出...                │
│   遇到安全问题时直接标记为BLOCKING..."     │
└─────────────────────────────────────────┘
```

### 2. 前端Reviewer Prompt的五大要素

| 要素 | 说明 | 示例 |
|------|------|------|
| **技术栈限定** | 明确框架和版本 | "基于React 19 + TypeScript 5.4" |
| **审查维度** | 定义检查项清单 | 性能、可维护性、安全性、可访问性 |
| **输出格式** | 结构化回复模板 | Markdown表格 + 严重程度标签 |
| **团队规范** | 内部约定 | "必须使用函数式组件"、"优先选useMemo" |
| **边界规则** | 什么不做 | "不评论代码风格（由ESLint处理）" |

### 3. 一个反直觉的发现

OpenAI和Anthropic的研究都表明：
> **具体、详细的System Prompt 优于 简短、模糊的Prompt**

不是"越简洁越好"，而是"越清晰越好"。一个200字的System Prompt通常比50字的更有效，前提是信息密度高、无冗余。

### 4. 常见陷阱

- **角色过载**：给AI太多身份（"你既是Reviewer又是Writer又是测试工程师"）→ 效果稀释
- **负面约束过多**："不要...不要..." → 模型更容易"记住"被禁止的行为
- **缺少输出样例**：只说"请详细说明"但没有给格式 → 每次输出不一致

## 代码实践（12分钟）

### 实战：设计你的「前端代码审查助手」System Prompt

以下是一个可直接使用的System Prompt模板，你可以根据团队规范调整：

```markdown
你是一位资深前端技术负责人，拥有8年以上React/TypeScript工程经验。
你的任务是对用户提交的代码进行专业审查。

## 技术背景
- 技术栈：React 19, TypeScript 5.4, Next.js 15
- 状态管理：优先使用React内置机制（useState/useReducer/Context）
- 样式方案：Tailwind CSS + CSS Modules
- 测试框架：Vitest + React Testing Library

## 审查维度（按优先级排序）
1. **正确性**：是否有潜在的运行时错误、类型不匹配、边界情况未处理
2. **性能**：是否有不必要的重渲染、内存泄漏、大数据量处理缺陷
3. **可维护性**：命名是否清晰、组件是否过度耦合、是否遵循单一职责
4. **安全性**：XSS风险、危险的DOM操作、敏感信息泄露
5. **可访问性**：ARIA属性、键盘导航、语义化标签

## 输出格式
对每一个问题，使用以下格式：

```
[严重程度] 维度：问题简述
- 位置：文件名（行号范围）
- 说明：具体原因
- 建议：如何修复（提供代码片段）
- 参考：相关文档链接（如有）
```

严重程度标签：🔴 BLOCKING（必须修复）/ 🟡 WARNING（建议修复）/ 🟢 SUGGESTION（可选优化）

## 特别规则
- 不要评论代码格式问题（由Prettier/ESLint处理）
- 如果代码没有明显问题，明确说"代码质量良好，无阻塞性问题"
- 审查意见要具体，避免空泛表述如"这里可以优化"
- 对React Hooks的使用尤其严格，检查依赖数组完整性
```

### 快速测试

用以下代码片段测试上面的System Prompt，观察AI的审查质量：

```tsx
// UserProfile.tsx
import { useState, useEffect } from 'react';

export function UserProfile({ userId }) {
  const [user, setUser] = useState(null);
  const [posts, setPosts] = useState([]);

  useEffect(() => {
    fetch(`/api/users/${userId}`)
      .then(r => r.json())
      .then(setUser);

    fetch(`/api/users/${userId}/posts`)
      .then(r => r.json())
      .then(setPosts);
  }, []);

  return (
    <div>
      <h1>{user.name}</h1>
      <p>{user.bio}</p>
      {posts.map(post => (
        <div key={post.id}>
          <h3>{post.title}</h3>
          <div dangerouslySetInnerHTML={{ __html: post.content }} />
        </div>
      ))}
    </div>
  );
}
```

> 💡 理想情况下，AI应该识别出：缺少userId依赖、无loading/error状态、XSS风险（dangerouslySetInnerHTML）、缺少TypeScript类型、可能的null引用（user.name）。

## 思考题（3分钟）

1. **边界问题**：如果你同时要求AI"严格审查"又"保持鼓励性语气"，这两个目标可能冲突吗？如何在Prompt中平衡？
2. **团队适配**：你当前团队的代码规范有哪些是"不成文"的？如何把这些隐性知识编码到System Prompt中？
3. **版本管理**：当团队技术栈升级（如React 18→19）时，你如何确保System Prompt同步更新？
