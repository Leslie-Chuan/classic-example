## 核心概念（5 分钟精读）

### 1. 为什么前端测试生成比后端更难？

后端 API 的输入输出边界清晰（请求参数 → 响应体），而前端组件的"正确性"包含多个维度：

| 维度 | 后端测试 | 前端测试 |
|------|---------|---------|
| 输入确定性 | 高（HTTP 请求） | 低（用户交互、浏览器事件、异步状态） |
| 输出验证 | 数据结构比对 | DOM 结构 + 视觉表现 + 交互反馈 |
| 环境依赖 | 数据库、缓存 | 浏览器渲染管线、CSS 计算、时序 |
| 副作用范围 | 可控 | 全局事件、localStorage、网络请求 |

这意味着，前端 AI 测试生成不能只给 LLM 一个组件源码就期待好结果——**上下文缺失是前端 AI 测试质量差的头号原因**。

### 2. LLM 生成测试的三种工作模式

在实际工程中，AI 测试生成通常以三种模式出现：

**模式 A：代码 → 单元测试（Code-to-Unit）**
- 输入：组件源码 + Props 类型定义
- 输出：Vitest/Jest + React Testing Library 测试用例
- 关键 Prompt 技巧：要求 LLM 关注"行为断言"而非"实现细节断言"

**模式 B：用户故事 → E2E 测试（Story-to-E2E）**
- 输入：产品需求描述或用户操作流程
- 输出：Playwright/Cypress 测试脚本
- 关键 Prompt 技巧：提供页面结构信息（如关键 data-testid 或 ARIA 角色）

**模式 C：运行时行为 → 回归测试（Runtime-to-Regression）**
- 输入：用户在浏览器中的真实操作序列（通过 Playwright codegen 或 session replay 录制）
- 输出：可重放的自动化脚本
- 这是目前最有前景的方向：AI 不是从零生成，而是"理解和增强"已有的行为记录

### 3. "伪覆盖"陷阱——AI 生成测试的最大风险

AI 生成的测试最常见的质量问题不是"测试失败"，而是**"测试通过了但没测到点上"**。典型表现：

- **全 Mock 陷阱**：所有外部依赖都被 mock，测试仅验证了"组件能渲染一个 div"
- **弱断言陷阱**：`expect(container).toBeTruthy()` 这类断言对行为零验证
- **时序脆弱陷阱**：未处理异步边界，测试在 CI 中随机失败
- **幻觉交互陷阱**：AI 虚构了不存在的 DOM 结构或事件处理器

**防御策略**：引入"断言强度检查"——要求 AI 生成的每个测试至少包含一个对业务行为的强断言（如状态变化、API 调用参数、DOM 内容变化）。

### 4. 测试即文档（Test as Documentation）的 AI 增强

在 AI 时代，测试代码的价值不仅是"验证正确性"，更是**"机器可读的组件使用说明书"**。一个设计良好的 AI 测试生成流程应该同时产出：
- 覆盖核心用例的测试代码
- 组件的隐式行为契约（如"当 userId 变化时会重新获取数据"）
- 边缘情况的显式记录（如"网络错误时显示错误信息"）

### 第一步：创建一个示例组件（`UserProfileCard.jsx`）

```jsx
import { useState, useEffect } from 'react';

/**
 * 用户资料卡片组件
 * @param {string} userId - 用户唯一标识
 * @param {function} onEdit - 点击编辑时的回调，参数为当前用户对象
 * @param {boolean} showAdminControls - 是否显示管理员操作按钮（删除）
 */
export default function UserProfileCard({ userId, onEdit, showAdminControls = false }) {
  const [user, setUser] = useState(null);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  useEffect(() => {
    let cancelled = false;
    setLoading(true);
    setError(null);

    fetch(`/api/users/${userId}`)
      .then(res => {
        if (!res.ok) throw new Error(`HTTP ${res.status}`);
        return res.json();
      })
      .then(data => {
        if (!cancelled) setUser(data);
      })
      .catch(err => {
        if (!cancelled) setError(err.message);
      })
      .finally(() => {
        if (!cancelled) setLoading(false);
      });

    return () => { cancelled = true; };
  }, [userId]);

  if (loading) {
    return <div data-testid="profile-skeleton">Loading profile...</div>;
  }

  if (error) {
    return (
      <div role="alert" className="error-banner">
        Failed to load profile: {error}
      </div>
    );
  }

  if (!user) return null;

  return (
    <article className="profile-card" data-testid="profile-card">
      <img src={user.avatar} alt={`Avatar of ${user.name}`} />
      <div className="profile-info">
        <h2>{user.name}</h2>
        <p>{user.bio || 'No bio available'}</p>
      </div>
      <div className="profile-actions">
        <button type="button" onClick={() => onEdit(user)}>
          编辑资料
        </button>
        {showAdminControls && (
          <button type="button" className="danger" onClick={() => {}}>
            删除用户
          </button>
        )}
      </div>
    </article>
  );
}
```

```javascript
/**
 * 调用真实 LLM API
 */
async function callRealLLM(prompt) {
  if (!CONFIG.OPENAI_API_KEY) {
    throw new Error('未设置 OPENAI_API_KEY，请设置环境变量或使用模拟模式');
  }

  const client = new OpenAI({ apiKey: CONFIG.OPENAI_API_KEY });
  const response = await client.chat.completions.create({
    model: CONFIG.MODEL,
    messages: [
      { role: 'system', content: '你是一个专业的前端测试代码生成助手。只输出代码，不输出解释。' },
      { role: 'user', content: prompt },
    ],
    temperature: 0.2,
    max_tokens: 4000,
  });

  return response.choices[0].message.content;
}

/**
 * 调用 LLM（根据配置决定真实或模拟）
 */
async function callLLM(prompt, type) {
  if (CONFIG.OPENAI_API_KEY) {
    console.log('正在调用真实 LLM 生成测试...');
    return callRealLLM(prompt);
  }

  console.log('使用模拟模式（设置 OPENAI_API_KEY 可调用真实 LLM）');
  await new Promise((r) => setTimeout(r, 800));
  return mockLLMResponse(type);
}

/**
 * 从 LLM 响应中提取代码块
 */
function extractCode(response) {
  const match = response.match(/```(?:jsx?|javascript)?\n?([\s\S]*?)```/);
  return match ? match[1].trim() : response.trim();
}

/**
 * 写入测试文件
 */
async function writeTestFile(code, type, componentName) {
  await fs.mkdir(CONFIG.OUTPUT_DIR, { recursive: true });

  const suffix = type === 'unit' ? '.test.jsx' : '.e2e.spec.js';
  const fileName = `${componentName}${suffix}`;
  const filePath = path.join(CONFIG.OUTPUT_DIR, fileName);

  await fs.writeFile(filePath, code + '\n', 'utf-8');
  console.log(`${type === 'unit' ? '单元测试' : 'E2E 测试'} 已生成: ${filePath}`);
  return filePath;
}

// ========== 主流程 ==========

async function main() {
  const targetFile = process.argv[2];

  if (!targetFile) {
    console.error('用法: node generate-tests.mjs <组件文件路径>');
    console.error('示例: node generate-tests.mjs ./UserProfileCard.jsx');
    process.exit(1);
  }

  const componentName = extractComponentName(targetFile);
  console.log(`目标组件: ${componentName}`);
  console.log(`模式: ${CONFIG.OPENAI_API_KEY ? '真实 LLM' : '模拟模式'}`);

  let sourceCode;
  try {
    sourceCode = await fs.readFile(targetFile, 'utf-8');
  } catch (err) {
    console.error(`无法读取文件: ${targetFile}`);
    process.exit(1);
  }

  console.log('正在生成单元测试...');
  const unitPrompt = buildUnitTestPrompt(sourceCode, componentName);
  const unitResponse = await callLLM(unitPrompt, 'unit');
  const unitCode = extractCode(unitResponse);
  await writeTestFile(unitCode, 'unit', componentName);

  console.log('正在生成 E2E 测试...');
  const e2ePrompt = buildE2EPrompt(sourceCode, componentName);
  const e2eResponse = await callLLM(e2ePrompt, 'e2e');
  const e2eCode = extractCode(e2eResponse);
  await writeTestFile(e2eCode, 'e2e', componentName);

  console.log('全部完成！生成的测试文件:');
  console.log(` - ${path.join(CONFIG.OUTPUT_DIR, componentName + '.test.jsx')}`);
  console.log(` - ${path.join(CONFIG.OUTPUT_DIR, componentName + '.e2e.spec.js')}`);
  console.log('提示：建议人工审查生成的测试，特别关注断言强度和 mock 合理性。');
}

main().catch((err) => {
  console.error('错误:', err.message);
  process.exit(1);
});
```

运行后，你会在 `__tests__/ai-generated/` 目录下得到两个可直接运行的测试文件。

### 代码中的关键设计决策

1. **Prompt 的结构化**：不是简单地把代码丢给 LLM，而是明确指定"行为维度"和"断言强度要求"。这是前端 AI 测试生成质量的分水岭。

2. **双模式架构**：模拟模式让任何人在无 API Key 的情况下都能体验完整流程；真实模式只需替换一个函数即可对接生产环境。

3. **竞态条件测试**：`userId` 变化时的请求清理测试，展示了 AI 生成测试不应只覆盖"Happy Path"。

4. **data-testid 与 ARIA role**：Prompt 中强制要求使用稳定的定位策略，避免生成脆弱的 CSS 选择器。

## 思考题（5 分钟）

### 问题一：伪覆盖的检测机制

AI 生成的测试用例在什么情况下会产生**"伪覆盖"**——即测试执行通过了，但并未真正验证关键业务逻辑？

以今天代码实践中的 `UserProfileCard` 为例，假设 AI 生成了如下测试：

```javascript
it('组件能渲染', () => {
  render(<UserProfileCard userId="1" onEdit={() => {}} />);
  expect(document.body).toBeTruthy();
});
```

这个测试"通过"了，但它验证了什么？**在实际工作中，你会如何设计一套"断言强度检查"机制，来自动识别并标记这类弱断言？** 是否可能通过 AST 分析测试代码，计算每个测试的"验证深度"（如是否触及了 props 回调、状态变化、DOM 内容）？

### 问题二：AI 测试生成的 CI/CD 集成与所有权

如果 AI 生成测试成为团队 CI/CD 流水线的标准环节，以下问题将变得尖锐：

1. **测试代码的所有权归属于谁？** 开发者、AI、还是团队共享资产？当测试失败时，责任边界如何划分？
2. **非确定性风险**：LLM 每次生成的测试可能略有不同，这会导致 CI 中的"测试抖动"（flakiness）。如何设计一个可回退的架构——既能利用 AI 生成能力，又能在 AI 输出不稳定时快速切回人工编写的基线测试？
3. **成本与延迟**：为每个 PR 调用 LLM 生成测试，在大型项目中可能产生显著的 API 成本和 CI 延迟。你会在什么粒度上触发 AI 测试生成（文件级、组件级、还是 PR 描述级）？

**请结合你所在团队的实际情况，思考上述三个问题的可行方案。**
