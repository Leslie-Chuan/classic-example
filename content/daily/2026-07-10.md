## 核心概念摘要

### 1. v0 的生成管线（Generation Pipeline）

一条 prompt 进入 v0 后，大致会经历以下阶段：

```
用户 Prompt
  ↓
意图解析（Intent Parsing）——识别页面/组件、交互、数据需求
  ↓
模板与上下文召回——从设计系统、主题、已有页面召回相关片段
  ↓
LLM 生成 TSX ——通常输出 React + Tailwind + shadcn/ui 组件
  ↓
AST / 渲染校验——确保代码可解析、可渲染、无危险副作用
  ↓
画布预览 + 可交互原型
  ↓
用户迭代反馈（循环）
```

关键点：

- **缩小生成空间**：强制输出 React + TypeScript + Tailwind，显著降低 LLM 的「自由度」。
- **模板召回**：v0 不是让模型凭空写页面，而是先匹配已有的组件模式或设计 token，再让模型填空。
- **渲染沙箱**：生成的组件在 iframe 或受限运行时中预览，防止不可信代码直接访问主应用状态。

### 2. 四层状态模型

v0 作为一个可迭代编辑器，其状态至少可以拆成四层：

| 状态层 | 作用 | 示例 |
|--------|------|------|
| Conversation | 记录用户与 AI 的多轮对话 | 提示词、修改指令、版本说明 |
| Generation | 某一次 LLM 生成的快照 | 生成的 TSX 代码、token 消耗、模型版本 |
| Canvas | 可视化编辑的当前视图 | 选中的组件块、展开的属性面板、交互模式 |
| Project | 跨页面/跨会话的工程级状态 | 页面路由、主题变量、依赖列表、导出配置 |

理解了这四层，就能解释 v0 为什么能做「撤销到任意版本」「多页面管理」「代码仓库同步」——它不是单纯保存 prompt，而是保存了完整的生成资产。

### 3. 可迭代编辑的架构支持

v0 真正的护城河不是「生成」，而是「改得动」。它依赖三种机制：

1. **块级 AST 定位**：把视觉上的选中区域映射到 TSX 的 AST 节点路径，让 AI 知道要改哪一部分。
2. **版本分支（Branching）**：每一次生成都是一次快照，用户可以在不同版本间切换、合并。
3. **受控重写（Constrained Rewrite）**：只让模型重写被指定的子树，而不是每次都全量生成，节省 token 也减少回归。

### 4. 产品权衡：可控 vs 创造

| 权衡 | v0 的选择 | 原因 |
|------|-----------|------|
| 通用模型 vs 微调 | 优先使用通用大模型 + 强 prompt/模板约束 | 降低维护成本，紧跟模型迭代 |
| 创造力 vs 可维护性 | 偏向可维护性：强类型、design token、可导出代码 | 让产物真正能被工程团队使用 |
| 封闭编辑器 vs 代码仓库 | 最终产物是可运行的 Next.js 项目 | 与 Vercel 部署生态绑定，也提升用户信任 |
| 自动生成 vs 人机协作 | 强调「人类在环路」——用户选、用户确认、用户部署 | 避免幻觉导致不可控的生产事故 |

## 代码实践：动手做一个「v0 风格」的组件生成校验脚本

**目标**：模拟 v0 的「生成后校验」环节，写一个最小 Node.js 脚本，检查 AI 生成的 TSX 组件是否符合预设的工程规范。

### 实践步骤（约 15 分钟）

1. 初始化项目并安装依赖：

```bash
mkdir mini-v0-lint && cd mini-v0-lint
npm init -y
npm install zod
```

2. 创建 `validate.tsx.mjs`：

```js
import { z } from 'zod';
import fs from 'fs';

// 1. 读取 AI 生成的组件文件
const code = fs.readFileSync(process.argv[2] || './Button.tsx', 'utf8');

// 2. 定义工程规范约束
const rules = z.object({
  hasTypeScriptExtension: z.literal(true),
  hasReactImport: z.boolean().refine(Boolean, { message: '缺少 React 导入' }),
  hasDefaultOrNamedExport: z.boolean().refine(Boolean, { message: '缺少组件导出' }),
  usesTailwind: z.boolean().refine(Boolean, { message: '未使用 Tailwind 类名' }),
  noHardcodedHexColors: z.boolean().refine(Boolean, { message: '检测到硬编码颜色，请使用 design token' }),
  hasPropsInterface: z.boolean().refine(Boolean, { message: '缺少 props 类型定义' }),
});

const report = {
  hasTypeScriptExtension: code.includes('.tsx') || true, // 这里从文件名判断
  hasReactImport: /import\s+.*['"]react['"]/.test(code),
  hasDefaultOrNamedExport: /export\s+(default\s+)?function|export\s+const/.test(code),
  usesTailwind: /className=["'][^"']*(bg-|text-|p-|m-)/.test(code),
  noHardcodedHexColors: !/#[0-9a-fA-F]{3,6}/.test(code),
  hasPropsInterface: /interface\s+\w+Props|type\s+\w+Props/.test(code),
};

// 3. 校验并输出结果
try {
  rules.parse(report);
  console.log('✅ 组件符合 v0 风格工程规范');
} catch (err) {
  console.error('❌ 规范检查未通过：');
  err.errors.forEach(e => console.error(`  - ${e.message}`));
  process.exit(1);
}
```

3. 写一个测试组件 `Button.tsx`：

```tsx
import React from 'react';

interface ButtonProps {
  children: React.ReactNode;
  onClick?: () => void;
  variant?: 'primary' | 'secondary';
}

export function Button({ children, onClick, variant = 'primary' }: ButtonProps) {
  return (
    <button
      onClick={onClick}
      className={`px-4 py-2 rounded ${
        variant === 'primary' ? 'bg-primary text-white' : 'bg-secondary text-black'
      }`}
    >
      {children}
    </button>
  );
}
```

4. 运行校验：

```bash
node validate.tsx.mjs ./Button.tsx
```

### 关键反思

> v0 的「护栏」不是限制 AI 的创造力，而是把创造力约束在工程团队能接受的形式里。这个脚本只是最简单的入口，真实系统还会加入 AST 解析、沙箱渲染、依赖审计等更复杂的校验。

## 今日小结

Vercel v0 的底层并不神秘：它把 LLM 的输出约束在 React + Tailwind 的轨道上，用 AST 和版本化状态让生成结果可以被反复编辑，再用「代码即真相」的方式把产物交还用户。今天我们用一个小脚本实践了「生成后校验」的思路，明天将进入 Bolt.new 的技术栈分析。
