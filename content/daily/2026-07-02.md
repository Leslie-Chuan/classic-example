# Day 71：从 AI Wrapper 到 AI Native 的设计演进

> 日期：2026-07-02  
> 模块：模块二 · LLM 在前端的落地应用  
> 预计学习时长：30 分钟

## 今日主题

理解 AI 应用从"简单封装 LLM API"（Wrapper）到"以 AI 为原生核心重新设计产品"（AI Native）的演进路径，掌握两者的架构差异与前端设计启示。

---

## 核心概念

### 1. AI Wrapper：在现有产品上加一层 AI

AI Wrapper 是最常见的起步形态：在原有功能前或后接入 LLM，用 AI 增强体验，但产品结构并未发生本质变化。

典型特征：
- 用户输入 → 调用 LLM API → 把结果塞回传统界面
- 状态模型仍是"请求-响应"，AI 只是可选增强层
- 失败时产品基本功能仍可独立运行

前端例子：在文档编辑器里加一个"AI 续写"按钮，或在评论区加一个"AI 生成回复"。

### 2. AI Native：AI 是产品的主循环

AI Native 应用把 LLM 放在产品交互的核心位置，用户与产品的每一次交互都围绕"人和 AI 协作"展开。

典型特征：
- 主界面不再是表单或列表，而是对话/流式协作空间
- 产品状态由用户意图、AI 输出、系统上下文共同驱动
- 失败时没有 AI，产品核心价值会大打折扣

前端例子：v0.dev、Bolt.new、Cursor——没有 AI，这些产品几乎不存在。

### 3. 从 Wrapper 到 Native 的三层跃迁

| 层级 | Wrapper 思维 | Native 思维 | 前端影响 |
|------|-------------|------------|---------|
| 交互层 | AI 作为按钮/插件 | AI 作为主界面 | 需要流式 UI、增量渲染、回退策略 |
| 数据层 | 静态数据 + 偶发 AI 调用 | 用户数据 + 上下文 + 模型输出共同构成状态 | 需要新的状态管理范式 |
| 架构层 | LLM 是外部依赖 | LLM 是系统组件之一，与工具、知识库、前端协同 | 需要 Agent Loop、Tool Use、RAG 集成 |

### 4. 设计原则：渐进式 AI 化

不是所有产品都需要一步变成 AI Native。更务实的路径：

1. **嵌入**（Embed）：在现有流程里加一个 AI 辅助入口。
2. **重构**（Refactor）：把 AI 输出变成核心工作流的一环，例如从"生成文案"到"AI 驱动页面搭建"。
3. **重塑**（Reimagine）：围绕 AI 能力重新设计产品形态，例如从"写代码"到"描述需求直接出应用"。

## 代码实践：一个可切换模式的 AI 组件

下面是一个简化示例，展示同一功能在 Wrapper 模式和 Native 模式下的不同交互形态。

```tsx
import { useState, useEffect } from 'react';

// Wrapper 模式：AI 是可选按钮
function WrapperMode({ initialContent }: { initialContent: string }) {
  const [content, setContent] = useState(initialContent);
  const [loading, setLoading] = useState(false);

  const enhanceWithAI = async () => {
    setLoading(true);
    const result = await fetch('/api/ai-enhance', {
      method: 'POST',
      body: JSON.stringify({ text: content }),
    }).then(r => r.text());
    setContent(result);
    setLoading(false);
  };

  return (
    <div>
      <textarea value={content} onChange={e => setContent(e.target.value)} />
      <button onClick={enhanceWithAI} disabled={loading}>
        {loading ? 'AI 优化中...' : '用 AI 优化文案'}
      </button>
    </div>
  );
}

// Native 模式：用户与 AI 共同编辑，流式反馈
function NativeMode({ goal }: { goal: string }) {
  const [draft, setDraft] = useState('');
  const [aiStream, setAiStream] = useState('');

  useEffect(() => {
    const es = new EventSource(`/api/ai-coedit?goal=${encodeURIComponent(goal)}`);
    es.onmessage = (e) => {
      setAiStream(prev => prev + e.data);
    };
    return () => es.close();
  }, [goal]);

  return (
    <div className="coedit-space">
      <div className="user-region">
        <h4>你的意图</h4>
        <input value={goal} readOnly />
        <textarea
          value={draft}
          onChange={e => setDraft(e.target.value)}
          placeholder="随时补充或纠正 AI..."
        />
      </div>
      <div className="ai-region">
        <h4>AI 协作输出</h4>
        <pre>{aiStream || '等待 AI 响应...'}</pre>
      </div>
    </div>
  );
}
```

### 实践要点

- Wrapper 模式关注"触发-等待-替换"，适合低风险增强。
- Native 模式关注"持续协作、流式呈现、状态共享"，适合把 AI 当作创作伙伴。
- 切换模式时，前端需要重新设计错误边界：Native 模式下 AI 失败必须有优雅的降级界面。

## 思考题

1. 你当前负责的产品中，哪些功能是"Wrapper 化"就能带来价值的？哪些必须重新设计交互才能释放 AI 潜力？
2. 如果一个 AI Native 功能在 10% 的情况下会输出不可用结果，前端应该如何设计回退策略，才能不让用户感到挫败？
3. 从"用户操作驱动界面"转变为"用户意图 + AI 输出共同驱动界面"，你的状态管理方案需要哪些变化？
