## 核心概念（约 10 分钟）

### 1. 多进程架构要解决什么问题？

早期的浏览器（如 IE、老版 Chrome 之前的浏览器）通常采用单进程架构：一个进程里跑所有标签页的 HTML 解析、JS 执行、网络请求、UI 渲染。这样会带来三个核心问题：

- **稳定性**：一个标签页崩溃，整个浏览器一起挂。
- **安全性**：网页的 JS 和渲染引擎拥有和浏览器主程序相同的权限，恶意页面容易攻击系统。
- **性能隔离**：一个页面占满 CPU/内存，会拖垮其他页面和浏览器 UI。

Chromium 的多进程架构把不同职责拆到独立进程，通过 IPC（现在是 Mojo）通信，从而实现了 **崩溃隔离、权限沙箱、资源隔离**。

### 2. 核心进程及其职责

| 进程类型 | 主要职责 | 前端开发者需要关注的点 |
|---|---|---|
| **Browser Process** | 地址栏、标签页管理、书签、扩展、权限弹窗、网络调度中枢、文件访问 | 主进程，所有渲染进程的"管家" |
| **Renderer Process** | HTML/CSS 解析、布局、绘制、JavaScript 执行（Blink + V8） | 每个标签页/站点可能对应一个进程；Site Isolation 后跨站 iframe 也会独立进程 |
| **GPU Process** | 接收绘制指令，调用 GPU 进行合成（compositing）、WebGL、视频硬解 | 卡顿、掉帧、层爆炸往往和它有关 |
| **Network Service** | 实际发起 HTTP/HTTPS/WebSocket 请求，管理连接池、缓存、Cookie | 从 Browser Process 中独立出来，Mojo 通信 |
| **Utility Process** | 音频、存储、PDF、打印、编解码等"工具型"任务 | 降低主进程负担，增强沙箱 |
| **Plugin Process** | 旧时代插件（PPAPI/Flash）容器 | 已基本退出历史舞台 |

### 3. 从 Legacy IPC 到 Mojo

Chromium 最初使用自研的 **Legacy IPC**，消息类型宏定义多、耦合强。2017 年后逐步迁移到 **Mojo**：

- **基于消息管道（Message Pipe）**：一对 endpoint，可跨进程也可同进程。
- **接口定义语言（Mojom）**：用 `.mojom` 文件定义接口，自动生成 C++ / JS / Java 绑定。
- **能力即服务**：Renderer 通过 Mojo 向 Browser 请求网络、存储、设备访问，而不是直接调用系统 API。
- **沙箱友好**：Renderer 进程被剥夺大部分系统调用权限，只能通过 Mojo 调用 Browser/GPU 等受信进程暴露的服务。

### 4. Site Isolation（站点隔离）

从 Chrome 67 开始默认开启：

- 同一站点（scheme + eTLD+1）的页面通常共享 Renderer。
- **不同站点的 iframe 会被放到不同 Renderer Process**，即使它们在同一个标签页里。
- 目的：防止 Spectre 类侧信道攻击读取其他站点的内存数据。

对前端的影响：

- `window.parent` / `window.postMessage` 跨域限制更严格。
- 跨站 iframe 的 DevTools 需要单独选择进程查看。
- 内存占用会增加，因为每个站点都有独立的 V8 实例和 Blink 状态。

### 5. 渲染进程的内部结构

一个 Renderer Process 内可能包含多个线程：

- **Main Thread**：JS 执行、DOM 操作、样式计算、布局（Layout）。
- **Compositor Thread**：接收输入事件、滚动、合成图层，不阻塞主线程。
- **Raster Thread（Pool）**：把图层栅格化成位图，交给 GPU Process。
- **IO Thread**：处理 IPC、网络数据接收。

理解这些线程边界，是排查卡顿（jank）和性能瓶颈的基础。

## 代码实践（约 15 分钟）

### 实践 1：用命令行参数观察 Chrome 进程

如果你本地安装了 Chrome，可以用以下命令启动一个独立实例，并打开 `chrome://memory-internals` 或 `chrome://process-internals`。

macOS 示例：

```bash
/Applications/Google\ Chrome.app/Contents/MacOS/Google\ Chrome \
  --user-data-dir=/tmp/chrome-dev-profile \
  --no-first-run \
  --new-window \
  "chrome://process-internals/#web-contents"
```

打开后访问几个不同站点（如 `github.com`、`news.ycombinator.com`、一个本地 SPA），观察：

- 每个标签页对应的 Renderer Process ID。
- 同一站点多个标签页是否共享 Renderer。
- 跨站 iframe 是否出现新的 Renderer Process。

### 实践 2：用 Puppeteer 验证多进程行为

创建一个 Node.js 脚本，观察不同页面是否运行在不同进程：

```js
// observe-processes.mjs
import puppeteer from 'puppeteer';

const browser = await puppeteer.launch({
  headless: false,
  args: ['--no-sandbox', '--process-per-site'],
});

const page1 = await browser.newPage();
await page1.goto('https://github.com');

const page2 = await browser.newPage();
await page2.goto('https://news.ycombinator.com');

// 在页面内读取当前进程的 PID（仅用于观察，生产环境不要用）
const pid1 = await page1.evaluate(() => {
  // Chrome 通过私有 API 暴露 processId
  if ('chrome' in window && chrome.processes) {
    return chrome.processes.getProcessId();
  }
  return 'unavailable';
});

console.log('Page 1 PID hint:', pid1);

// 更可靠的方式：通过 CDP 获取 TargetInfo
const targets = await browser.targets();
for (const t of targets) {
  if (t.type() === 'page') {
    console.log(`Target: ${t.url().slice(0, 60)}... | targetId: ${t.targetId()}`);
  }
}

// 保持窗口打开 10 秒，方便用 Activity Monitor / Task Manager 观察
await new Promise(r => setTimeout(r, 10000));
await browser.close();
```

运行：

```bash
npm init -y
npm install puppeteer
node observe-processes.mjs
```

尝试把 `args` 改成 `['--no-sandbox', '--single-process']`，对比进程数量差异。

### 实践 3：用 Chrome DevTools 观察线程

1. 打开任意网页，按 `Cmd/Ctrl + Shift + P`，输入 `Performance` 打开性能面板。
2. 录制 3-5 秒，滚动页面或点击按钮触发重绘。
3. 观察火焰图：
   - **Scripting**：Main Thread 上的 JS 执行。
   - **Rendering**：样式计算、布局、Layerize。
   - **Painting**：Raster 线程工作。
   - **GPU**：GPU Process 的合成工作。
4. 思考：哪些工作可以移到 Compositor Thread，哪些必须阻塞 Main Thread？
