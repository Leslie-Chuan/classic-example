# Day 18：Few-shot Prompting 在代码审查中的应用

> 适用人群：高级前端开发者（5年+经验）  
> 预计耗时：30分钟  
> 学习目标：掌握用 Few-shot Prompting 构建可复用的 AI 代码审查流程，理解示例工程化背后的设计权衡

---

## 今日主题（1分钟）

Few-shot Prompting 不是"给 AI 几个例子这么简单"。在代码审查这个高确定性、低容错率的场景中，它是一门关于"如何让模型快速习得团队隐性规范"的工程学。今天你将了解：如何从"随手丢给 AI 一段代码"进化到"用结构化示例驱动一致、可预期的审查输出"，并带走一套可直接嵌入 CI 流水线或 IDE 插件的审查引擎原型。

---

## 核心概念（5分钟精读）

### 1. 为什么代码审查特别适合 Few-shot？

代码审查天然具备"输入-输出"的清晰结构：**代码片段 → 审查意见**。与开放式文本生成不同，审查意见往往遵循团队固定的关注维度（性能、安全、可维护性、可访问性），且存在大量隐性规范——这些规范写进 System Prompt 会显得冗长且易过时，而通过精选示例传递则更为高效。

Few-shot 在代码审查中的独特优势在于：

- **规范内化**：模型从示例中推断团队的审查颗粒度和措辞风格，比规则列表更灵活
- **边界感知**：通过包含"通过审查"和"需要修改"的边界案例，模型学会区分"风格偏好"与"真正的问题"
- **低启动成本**：无需微调模型，仅需 3-5 个高质量示例即可在新项目上快速生效

### 2. 示例质量 > 示例数量

高级开发者最容易掉入的陷阱是：以为示例越多越好。实际上，**3 个精心设计的示例通常优于 10 个平庸示例**。核心原则：

- **覆盖审查维度**：每个示例应代表一个独立的审查关注点（如性能、类型安全、a11y）
- **展示推理痕迹**：在示例中显式写出"为什么这是问题"，而不仅是"怎么改"，引导模型输出可解释的审查意见
- **包含负例（Negative Example）**：提供一个"看起来有问题但实际上是合理实现"的代码，训练模型避免过度审查

### 3. 动态示例选择（Dynamic Example Retrieval）

静态 Few-shot 在面对大型代码库时会失效——一个 React Hook 的审查示例对 Node.js 工具函数毫无帮助。进阶做法是将示例库向量化，根据待审查代码的语义相似度动态检索 Top-K 示例：

```
待审查代码 → Embedding → 相似度搜索 → Top-3 相关示例 → 组装 Prompt
```

这本质上是把 Few-shot 和 RAG 结合，让审查能力随代码库增长而自适应扩展。

### 4. Prompt 结构的分层设计

一个工程化的代码审查 Prompt 应该分层：

- **Layer 1 - System**：定义审查者角色、输出格式、审查范围
- **Layer 2 - Few-shot Examples**：3-5 个按相关性排序的输入-输出对
- **Layer 3 - Context**：当前文件的类型、框架版本、团队特殊约定
- **Layer 4 - Input**：待审查的具体代码

这种分层确保了即使更换底层模型（GPT-4 → Claude → 本地模型），Few-shot 示例层也能保持稳定和可迁移。

### 可运行的 Few-shot 代码审查引擎

以下是一个基于 Node.js（v18+）的轻量级审查引擎，**无需外部依赖**，内置模拟模式可立即查看效果。你可以将其扩展为 CLI 工具、VS Code 插件或 GitHub Action。

**文件：`code-review-engine.js`**

```javascript
/**
 * Few-shot Code Review Engine for Frontend
 * 
 * 运行方式：
 *   1. 纯演示模式（无需 API Key）：node code-review-engine.js
 *   2. 接入 OpenAI（需设置 OPENAI_API_KEY）：OPENAI_API_KEY=sk-xxx node code-review-engine.js
 */

const EXAMPLES = [
  {
    category: "react-performance",
    code: `function UserList({ users }) {
  const [filter, setFilter] = useState('');
  const filtered = users.filter(u => u.name.includes(filter));
  
  return (
    <div>
      <input value={filter} onChange={e => setFilter(e.target.value)} />
      {filtered.map(u => (
        <UserCard key={u.id} user={u} onClick={id => console.log(id)} />
      ))}
    </div>
  );
}`,
    review: `## 审查意见

**[性能] onClick 回调导致子组件不必要重渲染**

每轮渲染都会创建新的箭头函数 `onClick={id => console.log(id)}`，导致 `UserCard` 的 props 引用变化，触发 React.memo 失效。

**建议修改：**
```js
const handleClick = useCallback((id) => {
  console.log(id);
}, []);
// 然后传递: onClick={handleClick}
```

**风险等级：** medium  
**维度：** performance`
  },
  {
    category: "typescript-safety",
    code: `async function fetchUser(id: string) {
  const res = await fetch(\`/api/users/\${id}\`);
  const data = await res.json();
  return data;
}`,
    review: `## 审查意见

**[类型安全] 返回类型未标注，依赖隐式 any**

`res.json()` 返回 `Promise<any>`，调用方无法获得类型提示，且运行时错误难以提前发现。

**建议修改：**
```ts
interface User {
  id: string;
  name: string;
  email: string;
}

async function fetchUser(id: string): Promise<User> {
  const res = await fetch(\`/api/users/\${id}\`);
  if (!res.ok) throw new Error(\`Failed: \${res.status}\`);
  const data: User = await res.json();
  return data;
}
```

**风险等级：** high  
**维度：** type-safety`
  },
  {
    category: "accessibility",
    code: `<div className="tab active" onClick={handleTabClick}>
  用户管理
</div>`,

**[可访问性] 交互元素缺少语义化标签和键盘支持**

使用 `<div>` 实现可点击区域，屏幕阅读器无法识别其角色；且缺少 `tabIndex` 和键盘事件，不符合 WCAG 2.1 标准。

**建议修改：**
```jsx

  className="tab active"
  onClick={handleTabClick}

</button>
```

**风险等级：** medium  
**维度：** accessibility`
  },
  {
    category: "negative-example",

**✅ 通过审查**

这是一个简洁、类型推导良好的自定义 Hook：
- 默认值参数提供良好的 DX
- 使用函数式更新避免闭包陷阱

**风险等级：** none

/**
 * 构建 Few-shot Prompt
 * 核心逻辑：根据代码类型选择相关示例 + 固定格式输出
 */
function buildReviewPrompt(codeToReview, fileType = 'jsx') {
  // 简单启发式：选择包含 React/TS/a11y 相关关键词的示例
  const relevantExamples = selectRelevantExamples(codeToReview, 3);

  const systemPrompt = `你是一位拥有 10 年经验的高级前端工程师，擅长 React、TypeScript 和性能优化。
审查代码时遵循以下原则：
1. 只指出真实的问题，避免风格偏好
2. 每个问题必须标注风险等级（high/medium/low）和维度（performance/type-safety/security/accessibility/maintainability）
3. 提供可直接应用的代码修改建议
4. 如果没有问题，明确输出"✅ 通过审查"`;

  let prompt = `${systemPrompt}\n\n`;
  prompt += `以下是几个审查示例，请遵循相同的格式和深度：\n\n`;

  relevantExamples.forEach((ex, idx) => {
    prompt += `--- 示例 ${idx + 1} [${ex.category}] ---\n`;
    prompt += `代码：\n\`\`\`\n${ex.code}\n\`\`\`\n`;
    prompt += `审查结果：\n${ex.review}\n\n`;
  });

  prompt += `--- 待审查代码 [${fileType}] ---\n`;
  prompt += `代码：\n\`\`\`\n${codeToReview}\n\`\`\`\n`;
  prompt += `审查结果：\n`;

  return prompt;
}

/**
 * 简单相关性选择器（生产环境可替换为 Embedding 相似度搜索）
 */
function selectRelevantExamples(code, k = 3) {
  const scores = EXAMPLES.map(ex => {
    let score = 0;
    const lowerCode = code.toLowerCase();
    const lowerEx = ex.code.toLowerCase();
    
    // 关键词匹配
    const keywords = ['usestate', 'useeffect', 'usecallback', 'usememo', 'async', 'fetch', 'onclick'];
    keywords.forEach(kw => {
      if (lowerCode.includes(kw) && lowerEx.includes(kw)) score += 2;
    });
    
    // 框架匹配
    if (lowerCode.includes('react') && lowerEx.includes('react')) score += 1;
    if (lowerCode.includes('typescript') || lowerCode.includes(': ') && lowerEx.includes(': ')) score += 1;
    
    // 负例始终保留一个
    if (ex.category === 'negative-example') score += 0.5;
    
    return { ex, score };
  });
  
  return scores
    .sort((a, b) => b.score - a.score)
    .slice(0, k)
    .map(s => s.ex);
}

/**
 * 模拟 LLM 输出（无需 API Key，用于快速验证 Prompt 结构）
 */
function mockLLMReview(prompt) {
  // 基于 prompt 中的代码内容进行简单模式匹配，模拟真实审查
  const codeMatch = prompt.match(/待审查代码.*?\n```\n([\s\S]*?)\n```/);
  if (!codeMatch) return '无法解析代码';
  
  const code = codeMatch[1];
  const issues = [];
  
  if (code.includes('useEffect') && !code.includes('useEffect(() =>') && code.includes('async')) {
    issues.push(`**[性能/可靠性] useEffect 回调直接声明为 async**
useEffect 回调返回 cleanup 函数，async 函数隐式返回 Promise，可能导致竞态条件和内存泄漏。

**建议：**
\`\`\`js
useEffect(() => {
  let cancelled = false;
  async function load() {
    const data = await fetchData();
    if (!cancelled) setData(data);
  }
  load();
  return () => { cancelled = true; };
}, []);
\`\`\`
**风险等级：** high  
**维度：** reliability`);
  }
  
  if (code.includes('dangerouslySetInnerHTML')) {
    issues.push(`**[安全] dangerouslySetInnerHTML 存在 XSS 风险**
直接注入 HTML 字符串可能导致 XSS，必须确保内容经过可信的清洗流程。

**风险等级：** high  
**维度：** security`);
  }
  
  if (issues.length === 0) {
    return `## 审查意见\n\n**✅ 通过审查**\n\n代码结构清晰，未发现明显问题。\n\n**风险等级：** none  
**维度：** none`;
  }
  
  return `## 审查意见\n\n${issues.join('\n\n')}`;
}

/**
 * 调用真实 LLM API（OpenAI 兼容格式）
 */
async function callLLM(prompt) {
  const apiKey = process.env.OPENAI_API_KEY;
  if (!apiKey) {
    console.log('[演示模式] 未检测到 OPENAI_API_KEY，使用模拟输出\n');
    return mockLLMReview(prompt);
  }

  const response = await fetch('https://api.openai.com/v1/chat/completions', {
    method: 'POST',
    headers: {
      'Content-Type': 'application/json',
      'Authorization': `Bearer ${apiKey}`
    },
    body: JSON.stringify({
      model: 'gpt-4o',
      messages: [{ role: 'user', content: prompt }],
      temperature: 0.2, // 低温度确保审查输出稳定、可预期
      max_tokens: 1500
    })
  });

  if (!response.ok) {
    throw new Error(`API 请求失败: ${response.status} ${await response.text()}`);
  }

  const data = await response.json();
  return data.choices[0].message.content;
}

/**
 * 格式化并输出审查结果
 */
function printReview(result, elapsedMs) {
  const line = '='.repeat(60);
  console.log('\n' + line);
  console.log('AI 代码审查报告');
  console.log(line);
  console.log(result);
  console.log(line);
  console.log(`⏱️  耗时: ${elapsedMs}ms`);
  console.log('提示：将 OPENAI_API_KEY 设为环境变量即可调用真实模型\n');
}

// ==================== 主程序 ====================

async function main() {
  // 待审查的代码（你可以修改这里测试自己的代码）
  const codeToReview = `function Dashboard() {
  const [data, setData] = useState(null);
  
  useEffect(async () => {
    const res = await fetch('/api/dashboard');
    const json = await res.json();
    setData(json);
  }, []);
  
  return <div dangerouslySetInnerHTML={{ __html: data?.summary }} />;
}`;

  console.log('🔍 正在构建 Few-shot Prompt...');
  const prompt = buildReviewPrompt(codeToReview, 'jsx');
  
  // 可选：打印完整 prompt 以便调试
  // console.log('\n--- 完整 Prompt ---\n', prompt, '\n---');

  const start = Date.now();
  const review = await callLLM(prompt);
  printReview(review, Date.now() - start);
}

main().catch(console.error);
```

### 关键扩展点

1. **接入真实 Embedding**：将 `selectRelevantExamples` 替换为向量检索（如使用 OpenAI embedding API 或本地模型），实现动态示例选择
2. **接入 CI 流水线**：将 `main()` 改为读取 git diff，在 pre-commit 或 PR 阶段自动审查变更文件
3. **IDE 集成**：将引擎封装为 VS Code 插件，利用 Language Server Protocol 实现实时审查
4. **示例库版本化**：将 EXAMPLES 存储为独立的 YAML/JSON 文件，支持团队通过 PR 流程更新审查规范

## 思考题（5分钟）

### 问题 1：示例污染与审查偏见

如果你的 Few-shot 示例全部来自项目 A 的代码库，而项目 B 使用了完全不同的状态管理方案（如从 Redux 迁移到 Zustand），AI 可能会基于示例中的 Redux 模式对 Zustand 代码给出不恰当的审查建议。**如何在 Few-shot 引擎中设计"示例版本控制"或"项目隔离"机制，避免示例污染导致的审查偏见？**

### 问题 2：审查疲劳与信号噪音

在大型 MR/PR 中，如果 AI 对每一行代码都输出"建议"，开发者很快会产生审查疲劳，真正重要的问题反而被淹没。**你会如何设计一个"信号分级"系统——让 Few-shot Prompting 不仅能发现问题，还能判断问题的"阻断性"，并在输出层面实现"仅当风险等级 ≥ high 时才阻止合并"的 CI 策略？**
