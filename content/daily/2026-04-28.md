## 【核心概念】（5分钟精读）

### 1. 生产级MCP Server的架构分层

GitHub MCP Server的源码（以及所有成熟的MCP Server）遵循清晰的三层架构：

```
┌─────────────────────────────────────────────┐
│  Transport & Protocol Layer                  │
│  (MCP SDK: Server/Transport/Schema)          │
├─────────────────────────────────────────────┤
│  Orchestration Layer                         │
│  (Tool Registry · Auth Middleware ·          │
│   Rate Limiter · Error Normalizer)           │
├─────────────────────────────────────────────┤
│  Domain Layer                                │
│  (IssueTools · PRTools · RepoTools ·         │
│   SearchTools · CodeTools ...)               │
└─────────────────────────────────────────────┘
```

**关键洞察**：大多数初学者的MCP Server直接把Domain层和Transport层混在一起。GitHub MCP的源码价值在于，它把"协议通信"和"业务逻辑"彻底解耦——这意味着你可以在不碰MCP协议细节的情况下，专注于GitHub API的封装质量。

### 2. 模块化Tool组织：领域驱动而非功能驱动

打开GitHub MCP的`src/tools/`目录，你会发现它不是按"增删改查"分类，而是按**业务领域**分类：

```
src/tools/
  ├── issues.ts      # Issue的创建、查询、评论、关闭
  ├── pulls.ts       # PR的创建、Review、Merge
  ├── repositories.ts # 仓库信息、分支、文件操作
  ├── search.ts      # 代码搜索、Issue搜索
  └── code.ts        # 文件内容、Blob、Tree
```

每个文件内部再按操作类型细分。这种组织的深层逻辑是：**MCP Tool的命名空间应该与用户的思维模型对齐**。当模型决定调用工具时，它通过工具名称和描述进行推理——`github_create_issue`比`github_post_v3_repos_issues`更容易被模型正确选择。

### 3. OAuth Scope → MCP Tool的动态映射

GitHub MCP最精妙的设计之一是**根据Token的权限动态调整暴露的Tools**。这不是MCP协议的要求，而是生产安全的必要设计：

```typescript
// 伪代码示意：GitHub MCP的权限过滤逻辑
const availableTools = allTools.filter(tool => {
  // 每个tool声明所需的OAuth scope
  const requiredScopes = tool.metadata.requiredScopes; // e.g., ["repo", "issues:write"]
  // 检查当前token是否具备这些scope
  return requiredScopes.every(scope => tokenScopes.includes(scope));
});
```

**为什么这很重要？** 假设用户只给了`read:org`权限的token，但Server暴露了一个`delete_repository`工具。模型可能在推理时选择这个工具，导致调用失败并产生一次无效的LLM往返。GitHub MCP在`initialize`阶段就过滤掉不可用的工具，让模型只看到"它能做的事"。

### 4. 速率限制：从HTTP Header到MCP错误

GitHub API有严格的速率限制（5000 requests/hour for authenticated users）。GitHub MCP的处理策略是：

1. **拦截HTTP 403/429响应**，提取`X-RateLimit-Remaining`和`X-RateLimit-Reset`
2. **将HTTP错误翻译为MCP错误格式**，但保留原始上下文
3. **在错误信息中嵌入恢复建议**（如"请在12:34后重试"），让模型有机会在对话中向用户解释

这比简单抛出`Error: 403 Forbidden`高明得多——因为接收错误的是LLM，不是人类开发者。错误信息本身也是Prompt的一部分。

### 5. 源码阅读的方法论：ASK框架

面对一个陌生的生产级代码库，建议用ASK框架：

- **A (Architecture)**：先看目录结构和入口文件，理解分层，不看具体实现
- **S (Surface)**：找一个你最熟悉的业务场景（如"创建Issue"），追踪完整的请求链路
- **K (Knobs)**：找出所有可配置点（环境变量、配置项），理解部署和定制方式

今天我们的代码实践将用这个框架解剖一个简化版的"类GitHub MCP Server"。

#### 1. 领域层：模块化Tool定义（domain/issues.ts）

```typescript
/**
 * domain/issues.ts
 * 模拟GitHub Issues的MCP Tool集合
 * 设计要点：每个Tool附带requiredScopes元数据，供上层做权限过滤
 */

import { z } from "zod";

// ── 输入校验Schema ───────────────────────────

export const CreateIssueSchema = z.object({
  owner: z.string().describe("仓库所有者"),
  repo: z.string().describe("仓库名"),
  title: z.string().min(1).max(256).describe("Issue标题"),
  body: z.string().optional().describe("Issue内容（Markdown）"),
  labels: z.array(z.string()).optional().describe("标签列表"),
});

export const ListIssuesSchema = z.object({
  owner: z.string(),
  repo: z.string(),
  state: z.enum(["open", "closed", "all"]).default("open"),
  per_page: z.number().min(1).max(100).default(30),
});

// ── Tool元数据类型 ───────────────────────────

export interface ToolDefinition {
  name: string;
  description: string;
  inputSchema: object;
  requiredScopes: string[];
  handler: (args: unknown) => Promise<{ content: Array<{ type: "text"; text: string }> }>;
}

// ── 模拟GitHub API的数据存储 ─────────────────

type Issue = {
  number: number;
  title: string;
  body?: string;
  state: "open" | "closed";
  labels: string[];
  created_at: string;
};

const mockDB = new Map<string, Issue[]>();
let globalIssueCounter = 100;

function getRepoKey(owner: string, repo: string) {
  return `${owner}/${repo}`;
}

// ── Tool实现 ─────────────────────────────────

export const createIssueTool: ToolDefinition = {
  name: "github_create_issue",
  description: "在指定仓库创建一个新的Issue。需要repo范围的写权限。",
  inputSchema: {
    type: "object",
    properties: {
      owner: { type: "string", description: "仓库所有者用户名" },
      repo: { type: "string", description: "仓库名称" },
      title: { type: "string", description: "Issue标题" },
      body: { type: "string", description: "Issue正文（支持Markdown）" },
      labels: { type: "array", items: { type: "string" }, description: "标签列表" },
    },
    required: ["owner", "repo", "title"],
  },
  requiredScopes: ["repo", "issues:write"],
  handler: async (args) => {
    const parsed = CreateIssueSchema.parse(args);
    const key = getRepoKey(parsed.owner, parsed.repo);

    const issue: Issue = {
      number: ++globalIssueCounter,
      title: parsed.title,
      body: parsed.body,
      state: "open",
      labels: parsed.labels || [],
      created_at: new Date().toISOString(),
    };

    const issues = mockDB.get(key) || [];
    issues.push(issue);
    mockDB.set(key, issues);

    return {
      content: [
        {
          type: "text" as const,
          text: `✅ Issue #${issue.number} 已创建\n标题: ${issue.title}\n状态: ${issue.state}\n标签: ${issue.labels.join(", ") || "无"}`,
        },
      ],
    };
  },
};

export const listIssuesTool: ToolDefinition = {
  name: "github_list_issues",
  description: "列出仓库中的Issue，支持按状态过滤。只需要repo范围的读权限。",
  inputSchema: {
    type: "object",
    properties: {
      owner: { type: "string" },
      repo: { type: "string" },
      state: { type: "string", enum: ["open", "closed", "all"], default: "open" },
      per_page: { type: "number", default: 30 },
    },
    required: ["owner", "repo"],
  },
  requiredScopes: ["repo"], // 读权限要求更低
  handler: async (args) => {
    const parsed = ListIssuesSchema.parse(args);
    const key = getRepoKey(parsed.owner, parsed.repo);
    const issues = mockDB.get(key) || [];

    const filtered =
      parsed.state === "all" ? issues : issues.filter((i) => i.state === parsed.state);

    const paginated = filtered.slice(0, parsed.per_page);

    const lines = paginated.map(
      (i) => `#${i.number} [${i.state.toUpperCase()}] ${i.title} | 标签: ${i.labels.join(", ") || "无"}`
    );

    return {
      content: [
        {
          type: "text" as const,
          text: `找到 ${paginated.length} 个Issue（共 ${filtered.length} 个）:\n${lines.join("\n") || "（无）"}`,
        },
      ],
    };
  },
};

// 导出问题域的所有Tool
export const issueTools = [createIssueTool, listIssuesTool];
```

#### 2. 编排层：权限过滤与速率限制（orchestration/gateway.ts）

```typescript
/**
 * orchestration/gateway.ts
 * 核心编排层：负责权限过滤、速率限制、错误统一处理
 * 这是GitHub MCP架构中最值得学习的部分
 */

import type { ToolDefinition } from "../domain/issues.js";

// ── 模拟OAuth Token的权限 ────────────────────

export interface AuthContext {
  token: string;
  scopes: string[];
  rateLimitRemaining: number;
  rateLimitReset: number;
}

/**
 * 从环境变量读取模拟的token配置
 * 格式: MOCK_TOKENS=[{"token":"ghp_xxx","scopes":["repo"]}]
 */
function loadMockTokens(): AuthContext[] {
  const raw = process.env.MOCK_TOKENS ||
    `[{"token":"ghp_demo_readonly","scopes":["repo"],"rateLimitRemaining":100,"rateLimitReset":${Date.now() + 3600000}}]`;
  return JSON.parse(raw);
}

const mockTokens = loadMockTokens();

// ── 认证中间件 ───────────────────────────────

export function authenticate(tokenHeader?: string): AuthContext {
  if (!tokenHeader) {
    throw new MCPAuthError("缺少Authorization头");
  }
  const token = tokenHeader.replace(/^Bearer\s+/i, "");
  const ctx = mockTokens.find((t) => t.token === token);
  if (!ctx) {
    throw new MCPAuthError("无效的token");
  }
  return ctx;
}

// ── 自定义错误类型 ───────────────────────────

export class MCPAuthError extends Error {
  constructor(message: string) {
    super(message);
    this.name = "MCPAuthError";
  }
}

export class MCPRateLimitError extends Error {
  constructor(public resetAt: number) {
    super(`API速率限制已达上限。请在 ${new Date(resetAt).toLocaleTimeString()} 后重试。`);
    this.name = "MCPRateLimitError";
  }
}

export class MCPScopeError extends Error {
  constructor(toolName: string, missing: string[]) {
    super(`调用 "${toolName}" 需要以下权限: ${missing.join(", ")}。当前token不具备这些权限。`);
    this.name = "MCPScopeError";
  }
}

// ── 速率限制中间件 ───────────────────────────

function checkRateLimit(ctx: AuthContext): void {
  if (ctx.rateLimitRemaining <= 0) {
    throw new MCPRateLimitError(ctx.rateLimitReset);
  }
  ctx.rateLimitRemaining--;
}

// ── 权限过滤：核心生产模式 ───────────────────

/**
 * 根据当前token的scopes，过滤出可用的Tool集合
 * 这正是GitHub MCP在initialize阶段做的事情
 */
export function filterToolsByScope(
  allTools: ToolDefinition[],
  ctx: AuthContext
): ToolDefinition[] {
  return allTools.filter((tool) => {
    const missing = tool.requiredScopes.filter((s) => !ctx.scopes.includes(s));
    return missing.length === 0;
  });
}

/**
 * 验证单次调用的权限（双重检查）
 */
export function assertToolPermission(tool: ToolDefinition, ctx: AuthContext): void {
  const missing = tool.requiredScopes.filter((s) => !ctx.scopes.includes(s));
  if (missing.length > 0) {
    throw new MCPScopeError(tool.name, missing);
  }
}

// ── 统一错误翻译器 ───────────────────────────

/**
 * 将底层错误翻译为LLM友好的MCP错误格式
 * 这是生产级Server的关键设计：错误信息本身就是Prompt的一部分
 */
export function normalizeError(err: unknown): { message: string; isError: true } {
  if (err instanceof MCPAuthError) {
    return { message: `🔒 认证失败: ${err.message}`, isError: true };
  }
  if (err instanceof MCPRateLimitError) {
    return { message: `⏳ ${err.message}`, isError: true };
  }
  if (err instanceof MCPScopeError) {
    return { message: `🛡️ 权限不足: ${err.message}`, isError: true };
  }
  if (err instanceof Error) {
    return { message: `❌ 执行错误: ${err.message}`, isError: true };
  }
  return { message: "❌ 未知错误", isError: true };
}

export { checkRateLimit };
```

#### 3. 协议层：MCP Server组装（server.ts）

```typescript
/**
 * server.ts
 * 协议层：将领域层和编排层组装为完整的MCP Server
 * 这一层应该"薄而稳定"，不包含业务逻辑
 */

import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import {
  CallToolRequestSchema,
  ListToolsRequestSchema,
} from "@modelcontextprotocol/sdk/types.js";

import { issueTools } from "./domain/issues.js";
import {
  authenticate,
  filterToolsByScope,
  assertToolPermission,
  checkRateLimit,
  normalizeError,
  type AuthContext,
} from "./orchestration/gateway.js";

// ── 模拟从环境/配置读取当前token ──────────────

const MOCK_AUTH_HEADER = process.env.MOCK_AUTH_HEADER || "Bearer ghp_demo_readonly";

// ── 初始化认证上下文 ─────────────────────────

let authContext: AuthContext;
try {
  authContext = authenticate(MOCK_AUTH_HEADER);
  console.error(`[Server] Token认证成功，scopes: [${authContext.scopes.join(", ")}]`);
} catch (e) {
  console.error("[Server] 认证失败，使用最小权限模式");
  authContext = { token: "none", scopes: [], rateLimitRemaining: 0, rateLimitReset: 0 };
}

// ── 权限过滤：决定暴露哪些Tool ───────────────

const allTools = [...issueTools];
const exposedTools = filterToolsByScope(allTools, authContext);

console.error(
  `[Server] 已注册 ${allTools.length} 个Tool，当前token可访问 ${exposedTools.length} 个`
);
exposedTools.forEach((t) => console.error(`  - ${t.name} (${t.requiredScopes.join(", ")})`));

// ── MCP Server初始化 ─────────────────────────

const server = new Server(
  {
    name: "github-like-mcp-server",
    version: "1.0.0",
  },
  {
    capabilities: {
      tools: {},
    },
  }
);

// ── Tool发现 ─────────────────────────────────

server.setRequestHandler(ListToolsRequestSchema, async () => {
  // 返回的是过滤后的Tool列表（不含handler，因为handler在Server内部路由）
  return {
    tools: exposedTools.map((t) => ({
      name: t.name,
      description: t.description,
      inputSchema: t.inputSchema,
    })),
  };
});

// ── Tool调用 ─────────────────────────────────

server.setRequestHandler(CallToolRequestSchema, async (request) => {
  const { name, arguments: args } = request.params;

  // 1. 查找Tool定义
  const tool = exposedTools.find((t) => t.name === name);
  if (!tool) {
    return {
      content: [{ type: "text", text: `错误: Tool "${name}" 不存在或当前token无权访问` }],
      isError: true,
    };
  }

  try {
    // 2. 双重权限检查（防御性编程）
    assertToolPermission(tool, authContext);

    // 3. 速率限制检查
    checkRateLimit(authContext);

    // 4. 执行Tool
    const result = await tool.handler(args);
    return result;
  } catch (err) {
    // 5. 统一错误处理
    const normalized = normalizeError(err);
    return {
      content: [{ type: "text", text: normalized.message }],
      isError: normalized.isError,
    };
  }
});

// ── 启动 ─────────────────────────────────────

async function main() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
  console.error("GitHub-like MCP Server running on stdio");
}

main().catch(console.error);
```

#### 5. 架构模式总结

```
请求链路: initialize → list_tools → call_tool
                    ↓              ↓

                    ↓              ↓
              返回可见Tools    checkRateLimit → handler → normalizeError
```

## 【思考题】（5分钟）

### 问题1：从"薄封装"到"厚抽象"的权衡

GitHub MCP Server本质上是一个**薄封装层**——它把GitHub REST API几乎1:1地映射为MCP Tool。但另一种设计思路是**厚抽象**——比如提供一个`github_code_review`工具，它在内部自动执行"获取PR diff → 获取相关Issue → 获取CI状态 → 生成审查摘要"的完整流程。

**请思考**：在AI时代，MCP Server应该倾向于"薄封装"还是"厚抽象"？从以下维度给出你的判断：
- **模型推理质量**：模型更容易正确使用原子操作还是复合操作？
- **错误可观测性**：当复合操作失败时，模型和用户如何定位问题？
- **可维护性**：GitHub API升级时，哪种设计更少需要修改？
- **你的实际场景**：如果你要为团队的内部平台构建MCP Server，你会选择哪种策略？

### 问题2：MCP Server的"供应链安全"

今天的代码示例中，`MOCK_AUTH_HEADER`是从环境变量读取的，真实场景中token可能来自：用户粘贴、OAuth流程、系统密钥管理器、CI/CD secrets。GitHub MCP Server需要处理token的**生命周期管理**（刷新、过期、吊销）。

更进一步的问题是：当你`npm install`一个第三方MCP Server时，它的代码会运行在你的机器上，拥有访问你本地文件系统和网络的能力。GitHub MCP是官方出品，但如果社区中出现一个`github-enhanced-mcp-server`，宣称提供更多功能，你如何设计一套**可复用的安全评估框架**来判断是否可以在生产环境中使用它？请从代码审计、运行时监控、权限最小化三个角度给出你的方案。
