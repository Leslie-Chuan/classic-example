## 核心概念

### 1. AI 落地页生成器不是“写代码的机器”，而是“意图 → 结构 → 资产 → 页面”的流水线

把 Builder 拆成四层，每一层都有明确的输入 / 输出：

```
用户意图（Prompt）
   ↓
[意图理解层]   → 输出：结构化需求（目标、受众、CTA、风格关键词）
   ↓
[结构设计层]   → 输出：页面大纲 + 组件编排方案（Hero / Features / Pricing / CTA / Footer）
   ↓
[内容生成层]   → 输出：文案、图片/图标描述、配色与排版 Token
   ↓
[代码生成层]   → 输出：可运行的组件代码 + 元数据（版本、依赖、可回滚点）
```

> 关键洞察：把 LLM 放在“结构层”和“内容层”之间反复调用，而不是一次性让它写完所有代码，质量会稳定得多。

### 2. Schema 优先 vs. 代码优先

两种生成策略对比：

| 策略 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| 代码优先 | 一次调用出结果，链路短 | 难校验、难回滚、幻觉多 | 快速原型 / Demo |
| Schema 优先 | 可校验、可版本化、便于多轮编辑 | 多一次模型调用、需要强类型定义 | 可上线产品 |

我们今天采用 **Schema 优先** 的简化版：先让 LLM 输出 JSON 页面描述，再渲染成组件。

### 3. 可靠性三件套

- **结构化输出（Structured Output / Zod）**：强制模型返回可解析格式
- **渲染沙箱（iframe 或 Worker）**：防止 AI 生成代码污染主页面或访问敏感 API
- **回退策略（Fallback）**：当生成失败或渲染报错时，降级到上一次可用版本或占位 UI

### 4. 最小可行产品（MVP）范围

30 分钟内，我们只覆盖：
1. 用户输入一句话需求
2. LLM 输出页面结构 JSON
3. 前端把 JSON 渲染成 Tailwind + React 组件
4. 提供“重新生成”和“复制代码”两个动作

不做的：真实支付、图片生成、后端持久化、A/B 测试。

## 代码实践：MVP 落地页生成器

### 阶段 1：页面 Schema 定义（5 分钟）

用一个 Zod Schema 把页面结构约束死，这是稳定性的根基：

```typescript
import { z } from 'zod';

export const SectionSchema = z.object({
  type: z.enum(['hero', 'features', 'pricing', 'testimonial', 'cta', 'footer']),
  headline: z.string().max(120),
  subheadline: z.string().max(200).optional(),
  cta: z.object({ text: z.string().max(40), href: z.string().default('#') }).optional(),
  items: z.array(z.object({ title: z.string(), description: z.string() })).optional(),
  style: z.object({
    tone: z.enum(['modern', 'playful', 'enterprise', 'minimal']),
    primaryColor: z.string().regex(/^#([0-9A-Fa-f]{6})$/),
  }).optional(),
});

export const PageSchema = z.object({
  title: z.string().max(80),
  description: z.string().max(200),
  sections: z.array(SectionSchema).max(6),
});

export type GeneratedPage = z.infer<typeof PageSchema>;
```

> 练习：把 `features` 和 `pricing` 的 `items` 字段约束更严格一些，例如要求 pricing 必须包含 price 字段。

### 阶段 2：服务端 Prompt 与结构化调用（10 分钟）

以 OpenAI / Anthropic 为例，核心是让模型输出 JSON 且可解析：

```typescript
// app/api/generate/route.ts
import { openai } from '@ai-sdk/openai';
import { generateObject } from 'ai';
import { PageSchema } from '@/lib/schema';

export async function POST(req: Request) {
  const { prompt } = await req.json();

  const { object } = await generateObject({
    model: openai('gpt-4o-mini'),
    schema: PageSchema,
    prompt: `你是一位资深落地页设计师。请根据以下用户需求，生成一个单页落地页的 JSON 描述。

用户需求："""${prompt}"""

要求：
- 页面最多 5 个 Section，必须包含 hero 和 cta
- 文案简洁、有说服力，符合目标受众
- 提供一个主色 hex 值，整体风格统一
- 输出必须是合法 JSON，符合给定 schema`,
    system: `你是一个专门生成落地页结构的 AI。只输出符合 schema 的 JSON，不要包含任何解释。`,
  });

  return Response.json(object);
}
```

> 注意：这里用了 `ai` SDK 的 `generateObject`，它会在后端自动处理 JSON 模式。如果不用 SDK，需要手动拼接 system prompt + `response_format: { type: 'json_object' }` + 额外的格式示例。

### 阶段 3：把 Schema 渲染成 React 组件（10 分钟）

渲染层只做一件事：根据 `section.type` 分发到对应组件，并把样式 token 注入上下文。

```tsx
// components/LandingPageRenderer.tsx
'use client';

import { GeneratedPage } from '@/lib/schema';
import { HeroSection } from './sections/HeroSection';
import { FeaturesSection } from './sections/FeaturesSection';
import { CTASection } from './sections/CTASection';

const sectionMap: Record<string, React.FC<{ data: any; theme: any }>> = {
  hero: HeroSection,
  features: FeaturesSection,
  cta: CTASection,
  // pricing / testimonial / footer 同理
};

export function LandingPageRenderer({ page }: { page: GeneratedPage }) {
  const theme = {
    primary: page.sections[0]?.style?.primaryColor ?? '#2563eb',
    tone: page.sections[0]?.style?.tone ?? 'modern',
  };

  return (
    <main className="min-h-screen bg-white">
      {page.sections.map((section, idx) => {
        const Component = sectionMap[section.type];
        if (!Component) return null;
        return <Component key={idx} data={section} theme={theme} />;
      })}
    </main>
  );
}
```

一个最小化的 Hero 组件示例：

```tsx
// components/sections/HeroSection.tsx
export function HeroSection({ data, theme }: { data: any; theme: any }) {
  return (
    <section
      className="py-20 px-6 text-center"
      style={{ backgroundColor: `${theme.primary}10` }}
    >
      <h1 className="text-4xl font-bold mb-4">{data.headline}</h1>
      {data.subheadline && (
        <p className="text-lg text-gray-600 mb-8 max-w-2xl mx-auto">
          {data.subheadline}
        </p>
      )}
      {data.cta && (
        <a
          href={data.cta.href}
          className="inline-block px-6 py-3 rounded-lg text-white font-medium"
          style={{ backgroundColor: theme.primary }}
        >
          {data.cta.text}
        </a>
      )}
    </section>
  );
}
```

### 阶段 4：渲染沙箱与回退（5 分钟）

把生成结果放进 `iframe` 渲染，并捕获错误：

```tsx
// components/SafePreview.tsx
'use client';

import { useState } from 'react';

export function SafePreview({ html }: { html: string }) {
  const [hasError, setHasError] = useState(false);

  if (hasError) {
    return (
      <div className="p-8 border rounded bg-red-50 text-red-700">
        <p className="font-medium">预览渲染失败</p>
        <p className="text-sm">已自动切换至上一次可用版本，或请重新生成。</p>
      </div>
    );
  }

  return (
    <iframe
      title="preview"
      srcDoc={html}
      className="w-full h-[600px] border rounded"
      sandbox="allow-scripts"
      onError={() => setHasError(true)}
    />
  );
}
```

> 思考点：`sandbox="allow-scripts"` 已经禁用了表单提交和弹窗，但如果页面需要加载外部字体或图标，应该怎么做？（答案：使用内联 SVG / Data URI，或把外部资源域名加入 CSP。）

## 思考题

1. **为什么“先出 Schema，再出组件”比直接让 LLM 写完整代码更可控？** 在你的实际项目中，哪些场景适合先做结构化约束？
2. 如果用户说“我要一个像 Airbnb 一样的页面”，模型很可能会过度设计。你会在 **Prompt 层** 还是 **Schema 层** 加什么约束来避免这种情况？
3. 今天的代码把样式 Token 放在了第一个 Section 里。如果不同 Section 的主色冲突，应该怎么设计更合理的 Theme 注入机制？
4. 在真实产品中，生成结果需要被编辑和版本化。你会如何设计“用户手动修改 → 保存为新版本 → 可对比 / 可回滚”的数据模型？

## 今日小结

今天我们用“意图 → Schema → 渲染 → 沙箱回退”这条链路，搭了一个 AI 落地页生成器的最小骨架。关键收获：

- Schema 是约束模型幻觉的第一道闸门；
- 渲染层越薄越好，组件库与数据结构解耦；
- 任何 AI 生成的产物都必须有版本、可回滚、可人工接管。
