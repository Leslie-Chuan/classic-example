## 一、今日主题（2分钟阅读）

过去几周我们学习了MCP协议、Agent架构、Prompt工程、RAG系统——这些AI工具链的核心能力都已就位。但有一个问题始终悬在头顶：**用户愿意为AI等待多久？**

研究表明，用户对AI生成内容的耐心阈值远低于传统页面加载：
- **Web页面**：3秒加载是可接受的
- **AI对话**：首token超过800ms就会产生"卡顿感"
- **代码补全**：超过200ms，开发者会打断当前流、手动输入

今天的核心问题是：**如何系统性地测量和优化AI工具链的响应速度？**

这不仅关乎"模型选多大"，更关乎前端工程化的每一个环节——从请求调度、流式传输到UI反馈的设计。

## 二、核心概念（8分钟精读）

### 2.1 AI工具链的延迟瀑布模型

一个完整的AI辅助请求（以Copilot类代码补全为例）经历的延迟瀑布：

```
用户按键 ──→ 上下文采集 (10-50ms)
              ├──→ AST提取 + 符号解析 (20-100ms)
              ├──→ 相关文件检索 (RAG, 30-200ms)
              ├──→ Prompt构建与截断 (5-20ms)
              ├──→ 网络请求建立 (TLS, 50-150ms)
              ├──→ 模型首Token生成 (TTFT, 200-2000ms) ← 最大瓶颈
              ├──→ 流式传输剩余Token (TBT, 10-50ms/token)
              └──→ 后处理与UI渲染 (5-30ms)
```

**两个关键指标**：
- **TTFT** (Time To First Token)：从请求发出到收到第一个响应字节的时间。由模型大小、队列深度、输入长度决定。
- **TBT** (Time Between Tokens)：相邻token之间的间隔。由模型推理吞吐量决定。

前端开发者能优化的通常是**TTFT之前**和**TBT之后**的环节——也就是"让模型更快地拿到正确输入"和"让用户体验不到延迟"。

### 2.2 感知性能 > 实际性能

在AI交互场景中，前端有一系列"障眼法"可以显著改善感知性能：

| 技术 | 原理 | 适用场景 |
|------|------|---------|
| **乐观UI** | 先显示预测结果，再异步校正 | 代码补全、简单重构 |
| **骨架屏/打字机** | 逐字显示让等待变得"可见" | 聊天对话、文档生成 |
| **预请求** | 用户还没按回车，上下文已准备好 | 代码补全（边输边预热） |
| **流式渲染** | token到达即渲染，不等待完整响应 | 所有长文本生成 |
| **局部更新** | 只重渲染变更的DOM节点 | diff视图、代码建议 |

> 核心洞察：AI场景下，"让用户看到进度"比"让用户更快看到结果"更重要。空白等待是最差的体验。

### 2.3 上下文构建的成本陷阱

TTFT的最大隐性成本来自**输入token的数量**。当你把半个项目的代码塞进Prompt时：
- 输入token费用线性增长（GPT-4o: $5/1M input tokens）
- 模型处理长上下文的注意力衰减（"Lost in the Middle"现象）
- 首token时间随输入长度显著增加

**优化策略三层模型**：

```
Layer 1: 减少输入（Least Input）
  ├── 代码摘要替代完整文件（AST提取接口签名）
  ├── 差异上下文替代完整文件（Git diff风格）
  ├── 层级摘要：package级 → module级 → function级

Layer 2: 缓存复用（Cached Context）
  ├── 系统Prompt、项目规范长期缓存
  ├── 文件索引预计算，避免每次重新解析
  ├── 向量检索结果本地缓存（LRU策略）

Layer 3: 并行预热（Pre-warmed）
  ├── 用户打开文件时，后台预热相关上下文
  ├── 预测用户下一步操作，提前构建Prompt
```

### 2.4 模型路由与降级策略

不是所有AI请求都需要最强模型。一个成熟的工具链应该具备**智能路由**能力：

```
用户请求
  ├── 简单问答（分类为Q&A）        → GPT-4o-mini / Claude 3 Haiku
  ├── 代码补全（需要低延迟）        → 专用补全模型 / 本地小模型
  ├── 复杂架构设计（需要高质量）     → GPT-4o / Claude 3.5 Sonnet
  └── 敏感代码分析（需要隐私保护）   → 本地部署的CodeLlama
```

**降级触发条件**：
- 主模型API超时（>3秒无首token）→ 自动切换到备用模型
- 速率限制(429) → 排队 + 切换到低成本模型
- 网络异常 → 本地缓存的模型响应或静态建议

## 三、代码实践（15分钟）

### 构建一个"AI工具链性能监控器"

我们将创建一个Node.js工具，用于测量和优化AI请求的完整链路性能。它能：
1. 记录每个阶段的耗时（上下文采集 → 首token → 完整响应）
2. 实现带超时的模型路由与自动降级
3. 模拟流式传输的感知性能优化

```typescript
// ai-perf-monitor.ts
// AI工具链性能监控与优化示例

import { performance } from 'perf_hooks';

// ========== 1. 性能追踪器 ==========

interface PerfSpan {
  name: string;
  start: number;
  end?: number;
  children: PerfSpan[];
}

class PerfTracker {
  private root: PerfSpan;
  private stack: PerfSpan[];

  constructor(taskName: string) {
    this.root = { name: taskName, start: performance.now(), children: [] };
    this.stack = [this.root];
  }

  start(name: string) {
    const span: PerfSpan = { name, start: performance.now(), children: [] };
    this.stack[this.stack.length - 1].children.push(span);
    this.stack.push(span);
  }

  end() {
    const span = this.stack.pop();
    if (span) span.end = performance.now();
  }

  report(): string {
    const lines: string[] = [];
    const walk = (span: PerfSpan, depth = 0) => {
      const duration = (span.end ?? performance.now()) - span.start;
      const indent = '  '.repeat(depth);
      lines.push(`${indent}${span.name}: ${duration.toFixed(1)}ms`);
      span.children.forEach((c) => walk(c, depth + 1));
    };
    walk(this.root);
    return lines.join('\n');
  }
}

// ========== 2. 模型路由与降级 ==========

type ModelTier = 'fast' | 'balanced' | 'quality';

interface ModelConfig {
  name: string;
  tier: ModelTier;
  timeoutMs: number;
  fallback?: string;
}

const MODEL_REGISTRY: Record<string, ModelConfig> = {
  'gpt-4o': { name: 'gpt-4o', tier: 'quality', timeoutMs: 8000, fallback: 'gpt-4o-mini' },
  'gpt-4o-mini': { name: 'gpt-4o-mini', tier: 'fast', timeoutMs: 3000, fallback: 'local-mock' },
  'claude-3-sonnet': { name: 'claude-3-sonnet', tier: 'balanced', timeoutMs: 6000, fallback: 'gpt-4o-mini' },
  'local-mock': { name: 'local-mock', tier: 'fast', timeoutMs: 500 },
};

interface AIRequest {
  prompt: string;
  preferredTier?: ModelTier;
  maxTokens?: number;
}

/**
 * 带超时和自动降级的AI请求封装
 */
async function callWithFallback(
  request: AIRequest,
  modelName: string = 'gpt-4o'
): Promise<{ text: string; modelUsed: string; spans: string }> {
  const tracker = new PerfTracker('ai-request');
  let currentModel = modelName;

  while (currentModel) {
    const config = MODEL_REGISTRY[currentModel];
    if (!config) throw new Error(`Unknown model: ${currentModel}`);

    tracker.start(`attempt-${config.name}`);
    tracker.start('context-prep');

    // 模拟上下文准备（AST提取、Prompt构建等）
    await sleep(15 + Math.random() * 30);
    tracker.end(); // context-prep

    tracker.start('network-and-ttft');

    try {
      const result = await Promise.race([
        simulateLLMCall(config, request),
        new Promise<never>((_, reject) =>
          setTimeout(() => reject(new Error('TIMEOUT')), config.timeoutMs)
        ),
      ]);

      tracker.end(); // network-and-ttft
      tracker.end(); // attempt

      // 模拟流式传输的剩余token时间
      tracker.start('streaming-tbt');
      await sleep(result.tokens * (config.tier === 'fast' ? 8 : 20));
      tracker.end();

      return { text: result.text, modelUsed: config.name, spans: tracker.report() };
    } catch (err) {
      tracker.end(); // network-and-ttft (可能没end，但report里会处理)
      tracker.end(); // attempt
      console.warn(`  ⚠️ ${config.name} failed: ${(err as Error).message}. Fallback → ${config.fallback}`);
      currentModel = config.fallback || '';
    }
  }

  throw new Error('All models exhausted');
}

// 模拟LLM调用（替换为真实API即可）
async function simulateLLMCall(
  config: ModelConfig,
  request: AIRequest
): Promise<{ text: string; tokens: number }> {
  // 模拟不同模型的延迟特征
  const baseLatency =
    config.tier === 'fast' ? 200 : config.tier === 'balanced' ? 600 : 1200;
  const jitter = Math.random() * 300;

  // 模拟偶发超时（5%概率）
  if (Math.random() < 0.05) {
    await sleep(config.timeoutMs + 1000);
  }

  await sleep(baseLatency + jitter);

  const tokens = Math.floor((request.maxTokens ?? 150) * (0.7 + Math.random() * 0.5));
  return {
    text: `[${config.name}] Generated ${tokens} tokens for: "${request.prompt.slice(0, 40)}..."`,
    tokens,
  };
}

function sleep(ms: number) {
  return new Promise((r) => setTimeout(r, ms));
}

// ========== 3. 流式输出优化演示 ==========

/**
 * 模拟"感知性能优化"的流式渲染器
 * 核心思想：token到达时不立刻渲染，而是批量+平滑输出
 */
async function* smoothStream(
  rawTokens: AsyncIterable<string>,
  options: {
    /** 最小批量大小 */
    minBatchSize?: number;
    /** 最大等待时间(ms) */
    maxWaitMs?: number;
    /** 目标输出速率(token/秒) */
    targetSpeed?: number;
  } = {}
) {
  const { minBatchSize = 3, maxWaitMs = 80, targetSpeed = 30 } = options;
  const targetInterval = 1000 / targetSpeed;

  let buffer: string[] = [];
  let lastFlush = performance.now();
  let tokenCount = 0;

  const iterator = rawTokens[Symbol.asyncIterator]();

  while (true) {
    const timeoutPromise = new Promise<'timeout'>((r) => setTimeout(() => r('timeout'), maxWaitMs));
    const nextPromise = iterator.next().then((v) => (v.done ? ('done' as const) : v.value));

    const result = await Promise.race([nextPromise, timeoutPromise]);

    if (result === 'timeout') {
      if (buffer.length > 0) {
        yield buffer.join('');
        buffer = [];
        lastFlush = performance.now();
      }
      continue;
    }

    if (result === 'done') {
      if (buffer.length > 0) yield buffer.join('');
      break;
    }

    buffer.push(result);
    tokenCount++;

    const now = performance.now();
    const timeSinceFlush = now - lastFlush;
    const expectedTokens = (timeSinceFlush / 1000) * targetSpeed;

    // 批量条件：数量达标 或 时间窗口足够 或 遇到标点
    const isPunctuation = /[。！？.!?\n]/.test(result);
    if (buffer.length >= minBatchSize || buffer.length >= expectedTokens || isPunctuation) {
      // 平滑节流：如果token来得太快，人为延迟以保持匀速
      const idealFlushTime = (tokenCount / targetSpeed) * 1000;
      const actualElapsed = now - lastFlush;
      if (actualElapsed < idealFlushTime) {
        await sleep(idealFlushTime - actualElapsed);
      }

      yield buffer.join('');
      buffer = [];
      lastFlush = performance.now();
    }
  }
}

// 模拟token源
async function* mockTokenSource(text: string, delayMs = 15) {
  for (const char of text) {
    await sleep(delayMs);
    yield char;
  }
}

// ========== 4. 主运行示例 ==========

async function main() {
  console.log('🚀 AI工具链性能优化 —— 运行演示\n');

  // --- 演示1：正常请求 ---
  console.log('【演示1】标准代码补全请求（期望fast tier）');
  const r1 = await callWithFallback(
    { prompt: 'Implement a useDebounce hook in React', preferredTier: 'fast', maxTokens: 120 },
    'gpt-4o'
  );
  console.log(`  ✅ 最终使用模型: ${r1.modelUsed}`);
  console.log(`  📊 性能瀑布:\n${r1.spans.split('\n').map((l) => '     ' + l).join('\n')}\n`);

  // --- 演示2：降级场景 ---
  console.log('【演示2】模拟主模型超时，触发降级链 gpt-4o → gpt-4o-mini → local-mock');
  // 强制让gpt-4o和gpt-4o-mini都超时（通过修改registry会污染全局，这里仅演示思路）
  // 实际运行中simulateLLMCall有5%概率超时，多跑几次就能看到降级
  let fallbackShown = false;
  for (let i = 0; i < 5 && !fallbackShown; i++) {
    try {
      const r2 = await callWithFallback(
        { prompt: 'Refactor this class to use composition', maxTokens: 200 },
        'gpt-4o'
      );
      if (r2.modelUsed !== 'gpt-4o') {
        console.log(`  ✅ 降级后使用模型: ${r2.modelUsed}`);
        fallbackShown = true;
      }
    } catch {
      console.log('  ❌ 全部模型超时（小概率事件）');
    }
  }
  if (!fallbackShown) console.log('  ℹ️ 本次运行未触发降级（5%概率，可多次运行观察）\n');
  else console.log('');

  // --- 演示3：流式平滑输出 ---
  console.log('【演示3】流式输出平滑化（对比原始 vs 平滑后）');
  const sampleText = '性能优化不仅是工程问题，更是用户体验设计的核心环节。';

  console.log('  原始流式（每个token间隔15ms，过快）：');
  const startRaw = performance.now();
  for await (const token of mockTokenSource(sampleText, 15)) {
    process.stdout.write(token);
  }
  console.log(`  ← 总耗时 ${(performance.now() - startRaw).toFixed(0)}ms`);

  console.log('\n  平滑流式（目标30 token/秒，批量+节流）：');
  const startSmooth = performance.now();
  for await (const batch of smoothStream(mockTokenSource(sampleText, 15), {
    targetSpeed: 30,
    minBatchSize: 2,
  })) {
    process.stdout.write(batch);
  }
  console.log(`  ← 总耗时 ${(performance.now() - startSmooth).toFixed(0)}ms\n`);

  console.log('💡 关键观察：平滑流式的总耗时更长，但用户感知更"稳定"，不会出现突然的爆发式输出。');
}

main().catch(console.error);
```

### 运行与观察重点

```bash
# 运行示例（需要TypeScript环境）
npx ts-node ai-perf-monitor.ts
```

1. **TTFT vs TBT**：观察性能报告中`network-and-ttft`和`streaming-tbt`的比例。对于短代码补全，TTFT占主导；对于长文档生成，TBT累积更可观。

2. **降级策略的实战化**：上面的代码使用随机超时模拟故障。在生产环境中，你应该根据HTTP状态码（429=限流、502/503=模型过载、524=超时）制定更精细的降级规则。

3. **平滑流式的取舍**：`smoothStream`通过牺牲总速度换取感知稳定性。对于聊天场景这是值得的；对于代码补全（用户急着看结果），应该降低`minBatchSize`甚至禁用平滑化。

**参考约束**：代码审查是"后台任务"（非阻塞），但用户打开审查面板后期望3秒内看到首批建议。如果单文件超过5000行，如何保持预算不被打破？

### 问题2：预请求（Pre-warming）的边界在哪里？

Day 51的核心理念之一是"让模型更快地拿到正确输入"。预请求策略（用户还没按下快捷键，后台已经在准备上下文）是其中的关键。

但预请求也有代价：
- **计算成本**：不必要的上下文构建会浪费CPU和API调用次数
- **隐私风险**：后台读取用户尚未请求的文件，可能触及敏感代码
- **缓存失效**：用户快速切换文件时，预计算的结果可能还没用就过期了

**你的任务**：设计一套"预请求决策算法"，决定什么时候应该预计算、什么时候应该等待。请描述你的触发条件、取消机制和命中率评估方法。

## 五、延伸阅读（4分钟）

### 1. 性能测量与基准测试
**《LLM推理性能优化指南》**（vLLM团队）  
https://docs.vllm.ai/en/latest/performance_benchmarking.html

vLLM是当前最流行的开源LLM推理引擎，其文档详细解释了TTFT、TBT、吞吐量之间的权衡关系。如果你计划部署本地模型（如CodeLlama或Qwen-Coder），这是必读材料。

### 2. 感知性能设计
**Vercel AI SDK 流式UI最佳实践**  
https://sdk.vercel.ai/docs/ai-sdk-ui/streaming

Vercel的AI SDK内置了`useStreamableText`、`useObject`等Hook，它们已经在内部实现了批量渲染和乐观更新。学习其源码可以深入理解"感知性能"的工程实现。

### 3. 上下文压缩前沿
**《The Cost of Context》**（Anthropic, 2025）  
https://www.anthropic.com/research/context-cost

Anthropic研究团队关于长上下文成本的分析。核心结论：即使是200K上下文窗口的模型，**前8K token的处理速度也是最后8K的3倍**。这意味着"把全部代码塞进去"不仅是费用问题，更是速度问题。

### 4. 前端专项优化
**GitHub Copilot的延迟优化实践**（推测与社区分析）  
- Copilot内部使用分层缓存：文件级 → 符号级 → 行级
- 代码补全采用"推测性执行"：根据已有输入预测完整请求，提前发往模型
- 当检测到用户快速连续输入时，会取消中间请求、只保留最后一个

可以在GitHub搜索`copilot latency`、`ai code completion caching`等关键词，找到社区对Copilot性能策略的逆向工程分析。
