## 【今日主题】（1分钟阅读）

**MCP（Model Context Protocol）** 是 Anthropic 在 2024 年底提出的开放协议，旨在标准化 AI 模型与外部世界的交互方式。它解决了一个核心问题：如何让 LLM 安全、统一地访问文件系统、数据库、API 和浏览器等外部资源，而不需要为每个工具单独写适配层。

对前端开发者而言，MCP 的意义在于——你正在从"调用 API 的人"转变为"定义 AI 可调用接口的人"。理解 MCP，等于拿到了 AI 时代工具链的通用语言门票。

---

## 【核心概念】（5分钟精读）

### 1. MCP 要解决的真正问题

在 MCP 出现之前，每个 AI 应用（Cursor、Claude Code、Copilot 等）都维护自己的工具集成逻辑。结果是：

- 工具碎片化：同样的 GitHub 操作，Cursor 和 Claude Code 各写一套
- 上下文割裂：模型无法在不同工具间共享上下文
- 安全失控：每个工具自行实现权限控制，标准不一

MCP 的核心思路很简洁：**把工具抽象为 Server，让 AI 应用作为 Client 通过统一协议调用**。类似于 USB-C 统一充电接口，MCP 试图统一 AI 与外部世界的连接方式。

### 2. 三层架构模型

```
┌─────────────────────────────────────┐
│  Host（宿主应用）                    │
│  Claude Desktop / Cursor / IDE      │
└─────────────┬───────────────────────┘
              │ 启动和管理多个 Client
┌─────────────▼───────────────────────┐
│  MCP Client（客户端）               │
│  维护与 Server 的 1:1 连接          │
│  处理能力发现、请求路由、错误处理     │
└─────────────┬───────────────────────┘
              │ stdio / SSE / HTTP
┌─────────────▼───────────────────────┐
│  MCP Server（服务端）               │
│  暴露具体能力：Tool / Resource /     │
│  Prompt，实际执行操作               │
└─────────────────────────────────────┘
```

关键点：**Host 可以管理多个 Client，每个 Client 连接一个 Server**。这意味着你的 IDE 可以同时连接 GitHub MCP Server、文件系统 MCP Server、数据库 MCP Server，模型可以在一次对话中跨多个工具协调操作。

### 3. 三种核心能力

| 能力 | 类比 | 用途 | 触发方式 |
|------|------|------|----------|
| **Tool** | 函数调用 | 执行动作（读文件、发请求、运行命令） | 模型主动调用 |
| **Resource** | 只读数据源 | 提供上下文（代码库结构、API Schema、文档） | Client 自动订阅或按需读取 |
| **Prompt** | 预设模板 | 封装复杂任务的 Prompt 模板（代码审查模板、重构模板） | 用户或模型引用 |

理解这三者的区别至关重要：**Tool 是动词（做某事），Resource 是名词（某数据），Prompt 是剧本（怎么做）**。模型在推理时决定调用哪个 Tool，而 Resource 是被动提供的上下文，Prompt 则是人类预置的最佳实践模板。

### 4. MCP 与 Function Calling 的本质区别

很多开发者会混淆 MCP 和 OpenAI 的 Function Calling。核心差异在于：

- **Function Calling** 是模型能力：模型输出 JSON 表示要调用的函数，由应用层解析执行。工具定义和实现都在应用内部。
- **MCP** 是协议层：它不关心模型如何决定调用工具，只定义 Client 和 Server 之间如何通信（能力发现、请求/响应格式、错误处理、生命周期管理）。

换句话说，Function Calling 是"模型怎么表达想调用工具"，MCP 是"工具提供方和 AI 应用怎么对接"。两者可以共存——MCP Server 的能力可以被转换为 Function Calling 格式供模型消费。

### 5. 传输层：stdio vs SSE

MCP 支持多种传输方式：

- **stdio**：本地子进程通信，Server 作为独立进程被 Host 启动。适合本地工具（文件系统、Git 操作）。
- **SSE（Server-Sent Events）**：HTTP 流式通信，适合远程服务或需要独立部署的 Server。
- **HTTP**：即将标准化的无状态传输方式。

stdio 是目前最常用的方式，因为它天然实现了"每个 Server 一个进程"的隔离模型，Host 可以通过进程管理控制生命周期和权限。

### 实践一：搭建一个文件系统 MCP Server

以下是一个完整的 Node.js MCP Server，提供读取文件、列出目录两个 Tool，以及一个代码库结构 Resource。

```typescript
// file-system-server.ts
// 运行：npx tsx file-system-server.ts

import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import {
  CallToolRequestSchema,
  ListToolsRequestSchema,
  ListResourcesRequestSchema,
  ReadResourceRequestSchema,
} from "@modelcontextprotocol/sdk/types.js";
import { promises as fs } from "fs";
import path from "path";

/**
 * 文件系统 MCP Server
 * 能力：
 * 1. Tool: read_file - 读取指定文件内容
 * 2. Tool: list_dir - 列出目录内容（支持过滤）
 * 3. Resource: codebase-structure - 返回项目根目录结构
 */

const ROOT_DIR = process.cwd();

const server = new Server(
  {
    name: "frontend-file-system-server",
    version: "1.0.0",
  },
  {
    capabilities: {
      tools: {},
      resources: {},
    },
  }
);

// ── Tool 定义 ──────────────────────────────

server.setRequestHandler(ListToolsRequestSchema, async () => {
  return {
    tools: [
      {
        name: "read_file",
        description: "读取指定路径的文件内容，支持自动检测编码",
        inputSchema: {
          type: "object",
          properties: {
            filePath: {
              type: "string",
              description: "相对于项目根目录的文件路径",
            },
            maxLines: {
              type: "number",
              description: "最多读取行数（防止大文件）",
              default: 200,
            },
          },
          required: ["filePath"],
        },
      },
      {
        name: "list_dir",
        description: "列出目录下的文件和子目录，支持按扩展名过滤",
        inputSchema: {
          type: "object",
          properties: {
            dirPath: {
              type: "string",
              description: "相对于项目根目录的目录路径",
              default: ".",
            },
            extension: {
              type: "string",
              description: "过滤扩展名，如 .ts .tsx .json",
            },
            recursive: {
              type: "boolean",
              description: "是否递归列出子目录",
              default: false,
            },
          },
          required: [],
        },
      },
    ],
  };
});

server.setRequestHandler(CallToolRequestSchema, async (request) => {
  const { name, arguments: args } = request.params;

  if (name === "read_file") {
    const filePath = path.resolve(ROOT_DIR, args.filePath as string);
    // 安全检查：防止路径遍历
    if (!filePath.startsWith(ROOT_DIR)) {
      throw new Error("Access denied: path outside project root");
    }

    const content = await fs.readFile(filePath, "utf-8");
    const maxLines = (args.maxLines as number) || 200;
    const lines = content.split("\n").slice(0, maxLines);

    return {
      content: [
        {
          type: "text",
          text: lines.join("\n"),
        },
      ],
    };
  }

  if (name === "list_dir") {
    const dirPath = path.resolve(ROOT_DIR, (args.dirPath as string) || ".");
    if (!dirPath.startsWith(ROOT_DIR)) {
      throw new Error("Access denied: path outside project root");
    }

    const entries = await fs.readdir(dirPath, { withFileTypes: true });
    const ext = args.extension as string | undefined;

    const items = entries
      .filter((entry) => {
        if (!ext) return true;
        return entry.isDirectory() || entry.name.endsWith(ext);
      })
      .map((entry) => ({
        name: entry.name,
        type: entry.isDirectory() ? "directory" : "file",
      }));

    return {
      content: [
        {
          type: "text",
          text: JSON.stringify(items, null, 2),
        },
      ],
    };
  }

  throw new Error(`Unknown tool: ${name}`);
});

// ── Resource 定义 ──────────────────────────

server.setRequestHandler(ListResourcesRequestSchema, async () => {
  return {
    resources: [
      {
        uri: "fs://codebase-structure",
        name: "codebase-structure",
        mimeType: "application/json",
        description: "项目根目录的文件结构概览（前两层）",
      },
    ],
  };
});

server.setRequestHandler(ReadResourceRequestSchema, async (request) => {
  const { uri } = request.params;

  if (uri === "fs://codebase-structure") {
    const buildStructure = async (dir: string, depth = 0): Promise<unknown> => {
      if (depth > 2) return "...";
      const entries = await fs.readdir(dir, { withFileTypes: true });
      const result: Record<string, unknown> = {};

      for (const entry of entries) {
        if (entry.name.startsWith(".")) continue; // 忽略隐藏文件
        if (entry.name === "node_modules") continue;
        const fullPath = path.join(dir, entry.name);
        if (entry.isDirectory()) {
          result[entry.name] = await buildStructure(fullPath, depth + 1);
        } else {
          result[entry.name] = "file";
        }
      }
      return result;
    };

    const structure = await buildStructure(ROOT_DIR);
    const json = JSON.stringify(structure, null, 2);

    return {
      contents: [
        {
          uri,
          mimeType: "application/json",
          text: json,
        },
      ],
    };
  }

  throw new Error(`Unknown resource: ${uri}`);
});

// ── 启动 Server ────────────────────────────

async function main() {
  const transport = new StdioServerTransport();
  await server.connect(transport);
  // stdio 模式下，日志不能输出到 stdout，否则干扰协议通信
  console.error("File System MCP Server running on stdio");
}

main().catch(console.error);
```

### 实践二：前端调用 MCP Server（浏览器环境模拟）

虽然 MCP 的 stdio 传输主要用于本地进程，但在前端开发场景中，我们经常需要让 Web 应用与 MCP Server 通信。以下展示如何通过 SSE 传输在前端调用 MCP Server 的能力：

```typescript
// mcp-client-browser.ts
// 这是一个概念演示，展示前端如何作为 MCP Client 与 Server 交互

interface MCPClient {
  listTools(): Promise<Tool[]>;
  callTool(name: string, args: Record<string, unknown>): Promise<ToolResult>;
  listResources(): Promise<Resource[]>;
  readResource(uri: string): Promise<ResourceContent>;
}

interface Tool {
  name: string;
  description: string;
  inputSchema: object;
}

interface ToolResult {
  content: Array<{ type: string; text: string }>;
}

interface Resource {
  uri: string;
  name: string;
  mimeType: string;
}

interface ResourceContent {
  contents: Array<{ uri: string; mimeType: string; text: string }>;
}

/**
 * 基于 SSE 的 MCP Client 实现
 * 实际项目中，Server 需要额外配置 SSE 传输层
 */
class BrowserMCPClient implements MCPClient {
  private baseUrl: string;
  private sessionId: string;

  constructor(baseUrl: string) {
    this.baseUrl = baseUrl;
    this.sessionId = crypto.randomUUID();
  }

  async listTools(): Promise<Tool[]> {
    const res = await fetch(`${this.baseUrl}/tools?sessionId=${this.sessionId}`);
    const data = await res.json();
    return data.tools;
  }

  async callTool(name: string, args: Record<string, unknown>): Promise<ToolResult> {
    const res = await fetch(`${this.baseUrl}/tools/call?sessionId=${this.sessionId}`, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ name, arguments: args }),
    });
    return res.json();
  }

  async listResources(): Promise<Resource[]> {
    const res = await fetch(`${this.baseUrl}/resources?sessionId=${this.sessionId}`);
    const data = await res.json();
    return data.resources;
  }

  async readResource(uri: string): Promise<ResourceContent> {
    const res = await fetch(
      `${this.baseUrl}/resources/read?uri=${encodeURIComponent(uri)}&sessionId=${this.sessionId}`
    );
    return res.json();
  }
}

// ── 使用示例 ───────────────────────────────

async function demo() {
  const client = new BrowserMCPClient("http://localhost:3000/mcp");

  // 1. 发现可用工具
  const tools = await client.listTools();
  console.log("可用工具:", tools.map((t) => t.name));

  // 2. 让 AI 调用工具分析代码
  const result = await client.callTool("read_file", {
    filePath: "src/components/Button.tsx",
    maxLines: 50,
  });
  console.log("文件内容:", result.content[0].text);

  // 3. 获取项目结构作为上下文
  const resource = await client.readResource("fs://codebase-structure");
  console.log("项目结构:", JSON.parse(resource.contents[0].text));
}

// demo().catch(console.error);

/**
 * 关键洞察：
 *
 * 1. MCP Client 的核心职责是"发现能力 + 转发请求"，不做业务逻辑
 * 2. 前端 MCP Client 通常运行在 Web Worker 或主线程，通过 SSE/HTTP
 *    与远程或本地 Server 通信
 * 3. 在 AI 应用中，Client 通常被封装在 Agent Loop 中：
 *    模型决定调用什么 -> Client 转发 -> Server 执行 -> 结果返回给模型
 */
```

### 实践三：在 React 中集成 MCP 能力的 Hook（高阶）

```typescript
// useMCPTool.ts
// 在 React 组件中优雅地调用 MCP Server 的能力

import { useState, useCallback } from "react";

interface UseMCPToolOptions {
  serverUrl: string;
  timeout?: number;
}

interface UseMCPToolResult<T> {
  data: T | null;
  loading: boolean;
  error: Error | null;
  execute: (args: Record<string, unknown>) => Promise<void>;
}

/**
 * 封装 MCP Tool 调用的 React Hook
 * 适合在 AI 驱动的 IDE 插件、低代码平台、智能文档系统中使用
 */
export function useMCPTool<T = unknown>(
  toolName: string,
  options: UseMCPToolOptions
): UseMCPToolResult<T> {
  const [data, setData] = useState<T | null>(null);
  const [loading, setLoading] = useState(false);
  const [error, setError] = useState<Error | null>(null);

  const execute = useCallback(
    async (args: Record<string, unknown>) => {
      setLoading(true);
      setError(null);

      try {
        const controller = new AbortController();
        const timer = setTimeout(
          () => controller.abort(),
          options.timeout || 30000
        );

        const res = await fetch(`${options.serverUrl}/tools/call`, {
          method: "POST",
          headers: { "Content-Type": "application/json" },
          body: JSON.stringify({ name: toolName, arguments: args }),
          signal: controller.signal,
        });

        clearTimeout(timer);

        if (!res.ok) {
          throw new Error(`MCP Server error: ${res.status} ${res.statusText}`);
        }

        const result = await res.json();
        // 根据 Tool 返回的 content 提取实际数据
        const text = result.content?.[0]?.text;
        setData(text ? (JSON.parse(text) as T) : (result as T));
      } catch (err) {
        setError(err instanceof Error ? err : new Error(String(err)));
      } finally {
        setLoading(false);
      }
    },
    [toolName, options.serverUrl, options.timeout]
  );

  return { data, loading, error, execute };
}

// ── 使用示例 ───────────────────────────────

/*
function ComponentAnalyzer() {
  const { data, loading, error, execute } = useMCPTool("read_file", {
    serverUrl: "http://localhost:3000/mcp",
```

## 【思考题】（5分钟）

### 思考题 1：权限模型的设计权衡

上面的文件系统 Server 示例中，安全控制只有一层"路径前缀检查"。在真实的企业级 AI 工具链中，MCP Server 的权限模型应该如何设计？

请思考：
- 如果 AI Agent 需要读取 `package.json` 来分析依赖，但又不能读取 `.env` 文件，这种细粒度权限应该如何表达？
- 当多个 MCP Server 同时运行时（文件系统 + GitHub + 数据库），如何防止 Agent 在跨 Server 调用时泄露敏感上下文？
- 前端开发者在构建 MCP Server 时，应该采用"默认允许 + 黑名单"还是"默认拒绝 + 白名单"的策略？

### 思考题 2：MCP 对前端工程化的深层影响

MCP 协议标准化了 AI 与工具的交互方式。假设你的团队正在开发一个内部设计系统平台，AI 需要能够：

1. 读取组件库源码（文件系统 MCP）
2. 查询组件使用频率（数据库 MCP）
3. 自动提交 PR 更新文档（GitHub MCP）
4. 在 Storybook 中预览修改结果（浏览器自动化 MCP）

**问题**：这种"多 Server 协作"的架构下，前端工程化体系（构建工具、组件库、文档站点、CI/CD）需要做哪些根本性的调整？传统的"编译 -> 打包 -> 部署"流水线，在 AI 可以随时读写代码和文档的世界里，是否还成立？
