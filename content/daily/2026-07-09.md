## 今日主题

**Vercel v0 是如何从「AI 生成 React 组件」进化为 AI Native 前端构建平台的？**

v0 最初是一个基于提示词生成 React 组件的实验性产品，后续逐步演化成支持迭代编辑、多页面、设计系统接入、代码导出的完整构建工具。理解它的架构演进，能帮助我们看清一个 AI Wrapper 如何走向 AI Native。

---

## 核心概念摘要

### 1. v0 的三代架构

| 阶段 | 时间 | 核心形态 | 技术特征 |
|------|------|----------|----------|
| v0.1 | 2023 秋 | 单组件生成器 | 基于 Tailwind + shadcn/ui 的 prompt-to-TSX |
| v0.2 | 2024 春夏 | 可迭代画布 | 块级编辑、版本分支、多轮对话式修改 |
| v0.3 | 2024 秋至今 | AI Builder 平台 | 多页面项目、主题系统、代码仓库同步、部署到 Vercel |

### 2. 关键技术决策

- **生成目标锁定 React + Tailwind**：降低 LLM 输出空间，提升可渲染成功率。
- **组件级可编辑而非全量重生成**：用 AST + 视觉选择器定位修改点，减少 token 消耗。
- **设计 token 与主题系统**：让 AI 的输出可以被品牌规范约束，而不是每次重新发明样式。
- **代码即真相（Code as Source of Truth）**：最终产物是可在本地运行的 Next.js 项目，而非封闭的私有格式。

### 3. AI Native  vs AI Wrapper 的对比

| AI Wrapper | AI Native |
|------------|-----------|
| 一次性生成内容 | 生成结果作为可迭代资产 |
| 用户负责后续维护 | 系统维护状态、版本与依赖 |
| 输出是终点 | 输出是持续协作的起点 |
| 以 prompt 为中心 | 以生成的应用对象为中心 |

v0 的演进本质，就是把「生成组件」变成「管理一个由 AI 辅助的设计-编码-部署闭环」。

## 代码实践：用结构化 prompt 约束 AI 输出可维护组件

**目标**：当让 AI 生成一个表单组件时，不只要「能跑」，还要「可改、可复用」。

### 实践步骤（约 15 分钟）

1. 打开任意 AI 编码助手（Claude / v0 / Cursor）。
2. 粘贴以下 prompt 模板：

```markdown
请帮我生成一个 React 登录表单组件，要求：

- 使用 TypeScript + React Hook Form + Zod 做类型与校验
- 样式使用 Tailwind CSS，颜色变量从 design tokens 引入
- 拆分为三个文件：LoginForm.tsx、schema.ts、types.ts
- 表单字段：email、password、rememberMe
- 支持 loading 和 error 状态，并预留 onSubmit 回调类型
- 不要硬编码中文，使用 props 传入 labels
```

3. 检查 AI 输出是否满足：
   - 是否拆分文件？
   - 是否有清晰的类型定义？
   - 样式是否使用了语义化 token 而非具体色值？
   - 是否暴露了可配置的 props？

### 关键反思

> 生成代码的「一次性成功率」不是最重要的，**可维护的边界与约定**才是 AI Native 工具的核心。
