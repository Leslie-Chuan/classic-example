## 核心概念（15 分钟阅读）

### 1. 开源社区的权力结构与文化规则

**显性规则 vs 隐性规则**
- 显性规则写在 CONTRIBUTING.md 和 CODE_OF_CONDUCT.md 里：代码风格、Commit规范、PR模板
- 隐性规则需要观察学习：维护者的决策偏好、社区的讨论节奏、"政治正确"的技术观点

**权力分层（以典型中型项目为例）**
```
项目创始人/Owner
    └── 核心维护者（Merge权限 + 发布权限）
            └── 常驻贡献者（长期活跃，熟悉代码库）
                    └── 活跃贡献者（定期提交PR）
                            └── 偶尔贡献者（一次性PR）
                                    └── 用户（只提Issue）
```

**融入社区的秘诀**
- 前3个PR保持"小而美"：让维护者对你产生"这人不添乱"的第一印象
- 在Issue区先回答问题，再提自己的方案：展示你对项目的理解深度
- 尊重维护者的时间：PR描述写得像给CEO汇报，而不是给同事闲聊

### 2. 如何高效阅读大型开源项目源码

**倒金字塔阅读法**
不要从 `src/index.ts` 第一行开始读。采用由表及里的策略：

1. **接口层**（5分钟）：先看 public API 和类型定义，了解项目对外暴露什么能力
2. **架构层**（10分钟）：看目录结构和核心模块的依赖关系图，理解数据流向
3. **实现层**（按需深入）：针对你关心的功能，追踪具体实现代码

**实战技巧：用Git历史理解设计决策**
```bash
# 查看某个文件的修改历史
gh api repos/用户名/项目名/commits --path src/core/agent.ts | jq '.[].commit.message'

# 找到引入某个功能的那次Commit
git log --all --full-history --source -- src/core/agent.ts

# 查看PR讨论，理解"为什么这样设计"
gh pr view 123 --comments
```

**前端项目源码速览清单**
```
□ package.json — 依赖图谱揭示技术选型逻辑
□ tsconfig.json — 编译目标判断兼容性策略
□ src/index.ts 或 src/index.js — 入口文件看暴露接口
□ tests/ 目录 — 测试用例是最好的使用文档
□ .github/workflows/ — CI流程暴露项目质量标准
```

### 3. 高质量PR的设计原则

**好的PR不是"能运行"，而是"能被合并"**

**原则一：原子性**
- 一个PR只解决一个问题
- 不要把"修复Bug + 重构代码 + 更新文档"塞进同一个PR
- 如果改动超过300行，考虑拆分成多个PR

**原则二：自解释性**
- PR标题用动词开头：`Fix memory leak in stream parser` 而非 `Update parser.ts`
- 描述中包含"问题-方案-验证"三段论
- 附上截图或GIF（如果是UI改动）

**原则三：降低评审成本**
```markdown
## 改动摘要
修复了流式解析器在处理大模型输出时的内存泄漏问题

## 复现步骤
1. 启动本地开发服务器：`npm run dev`
2. 发送一个超过4000 token的prompt
3. 观察Chrome DevTools Memory面板，堆内存持续上升

## 解决方案
在 `StreamParser` 的 `onChunk` 回调中，添加 `this.buffer.trim()` 
清理已处理的token缓存。参考React的Scheduler内存管理策略。

## 验证
- [x] 本地复现了泄漏场景
- [x] 修复后重复相同步骤，内存保持稳定
- [x] 添加了回归测试：`test/stream-parser-memory.test.ts`
- [x] 现有测试全部通过：`npm test`（42/42 passed）
```

### 4. 与维护者建立信任的长期策略

**信任积累曲线**
- 第1-3个PR：证明你能遵循规范，不增加维护负担
- 第4-10个PR：开始在Issue区给出有价值的评论，展示领域知识
- 第10+个PR：主动认领复杂Issue，提出RFC（Request for Comments）

**有效沟通的DO和DON'T**

| ✅ DO | ❌ DON'T |
|-------|----------|
| "我测试了3种方案，A方案最简单但性能差，B方案复杂但可维护，建议选B" | "我觉得应该这样做" |
| "这个改动可能破坏向后兼容，需要讨论" | 直接提交破坏性改动 |
| 在讨论中@相关维护者，但只@真正相关的人 | @所有维护者求关注 |
| 承认自己的错误："你说得对，我重新修改了" | 防御性反驳每条评论 |

### 5. 可持续贡献的时间管理

**避免"激情燃烧殆尽"**
- 设定每周上限：比如每周最多2小时开源贡献
- 把贡献融入工作流：使用工具时遇到的Bug，顺手修掉
- 不要承诺你无法兑现的Deadline："我下周试试"比"我明天一定完成"更安全

## 代码实践（12 分钟动手）

### 实践：分析一个真实Issue并设计解决方案

以 Continue.dev 的一个假设Issue为例（你也可以去该项目找真实Issue练习）：

**Issue #1842（假设）：流式输出时 Markdown 代码块渲染闪烁**

**问题描述**：当AI返回包含代码块的Markdown时，流式渲染导致代码高亮频繁重绘，产生视觉闪烁。

**你的任务**：在12分钟内完成以下分析

**步骤1：定位相关代码（3分钟）**
```bash
# 在项目中搜索与"stream"和"markdown"相关的文件
grep -r "stream" src/components --include="*.ts" --include="*.tsx" | head -20
grep -r "Markdown" src/components --include="*.tsx" | head -20
```

假设你找到 `src/components/Chat/StreamedMarkdown.tsx`，关键代码：
```tsx
// 当前实现（简化版）
export function StreamedMarkdown({ content }: { content: string }) {
  return <ReactMarkdown components={{ code: CodeBlock }}>{content}</ReactMarkdown>;
}
```

**步骤2：分析问题根因（4分钟）**
每次 `content` 更新（流式接收新token），`ReactMarkdown` 都会重新渲染整个文档树。如果 `content` 从 `"```js\nconsole"` 变成 `"```js\nconsole.log"`，代码块组件会卸载并重新挂载，导致：
1. 语法高亮重新计算
2. 滚动位置可能跳动
3. 视觉闪烁

**步骤3：设计优化方案（5分钟）**

方案A：增量渲染（Incremental Rendering）
```tsx
// 将内容按行分割，只对新增行做高亮
const lines = content.split('\n');
return (
  <div>
    {lines.map((line, i) => (
      <MemoizedLine key={`${i}-${line}`} content={line} />
    ))}
  </div>
);
```

方案B：防抖渲染（Debounced Rendering）
```tsx
const debouncedContent = useDebounce(content, 100); // 100ms内不更新
return <ReactMarkdown>{debouncedContent}</ReactMarkdown>;
```

方案C：虚拟化 + 增量解析
使用 `remark` 的增量解析能力，只更新变更的AST节点。

**你的选择**：在真实场景中，你会如何权衡？把你的分析写成一条Issue评论或PR描述草稿。

> 💡 **学习提示**：开源世界里有一句话——"Talk is cheap, show me the code"。但更深层的真相是："Code is cheap, show me the context"。维护者更愿意合并那些"理解项目上下文、尊重现有设计、解决真实问题"的贡献，而不是那些"技术酷炫但增加维护负担"的PR。深度参与的本质，是让自己成为项目上下文的持有者。
