## 今日主题

**AI生成React组件的可靠性保障**

当 LLM 直接生成可运行的 React 组件代码时，我们面对的是一个「概率性代码生成器」：输出可能包含语法错误、类型不匹配、不安全 API 调用，甚至幻觉属性。今天的学习重点是：如何为 AI 生成的组件建立多层可靠性防线，让生成式 UI 从「Demo 玩具」走向「生产可用」。

---

## 核心概念

### 1. 为什么 AI 生成的组件不可靠？

LLM 生成代码的本质是「基于上下文的 token 概率预测」，它并不真正理解运行时语义。常见风险包括：

- **语法错误**：遗漏括号、引号、import 语句
- **类型不匹配**：臆造 props、错误的事件处理类型
- **运行时错误**：访问未定义变量、不安全的 `eval`、无限循环
- **安全漏洞**：XSS（如直接渲染未过滤的 HTML/JS）、危险依赖
- **版本幻觉**：使用已废弃 API（如 React 18 还在用 `ReactDOM.render`）

### 2. 可靠性保障的四层防线

| 层级 | 目标 | 常用手段 |
|------|------|----------|
| **生成约束层** | 让模型输出更结构化 | JSON Mode / Function Calling、Zod Schema、组件模板 |
| **静态验证层** | 在运行前发现错误 | ESLint、TypeScript 类型检查、Babel 解析、AST 校验 |
| **运行时隔离层** | 防止错误扩散 | Error Boundary、iframe 沙箱、Web Worker、Shadow DOM |
| **人工回退层** | 保留最终控制权 | 人工确认、Diff 预览、一键回滚、A/B 对比 |

### 3. 关键策略详解

#### 3.1 结构化生成：从「自由文本」到「受控 Schema」

不要直接让 LLM 输出 JSX 字符串。更好的方式是让它输出**结构化的组件描述**，再由渲染器转换为真实组件：

```json
{
  "componentType": "Button",
  "props": {
    "variant": "primary",
    "children": "提交",
    "onClick": "handleSubmit"
  },
  "style": { "marginTop": "16px" }
}
```

这种方式可以显著降低幻觉，并且便于前端做白名单校验。

#### 3.2 使用 Error Boundary 做运行时兜底

即使通过了静态校验，运行时仍可能出错。Error Boundary 是 React 中隔离生成组件错误的必备手段。

#### 3.3 iframe / Shadow DOM 做视觉与执行隔离

对于完全不可信的生成代码，可以放入 `iframe` 或 Web Component 的 Shadow DOM 中执行，避免污染主应用的 DOM、样式和全局状态。

#### 3.4 版本锁定与依赖白名单

AI 模型训练数据有截止日期，可能推荐过时依赖。生产环境应：

- 锁定 React / Next.js / 组件库版本
- 维护「允许使用的依赖白名单」
- 禁止动态 `import()` 未审核的第三方包

## 代码实践

### 实践目标

实现一个 **AI 生成组件的安全渲染器**，包含：
1. 对生成代码做基础语法检查（通过 Babel 解析）
2. 使用 Error Boundary 捕获运行时错误
3. 提供 fallback UI

### 完整代码

```tsx
// SafeComponentRenderer.tsx
import React, { Component, Suspense, useState, useCallback } from 'react';
import * as Babel from '@babel/parser';

interface Props {
  code: string; // AI 生成的组件代码字符串
  fallback?: React.ReactNode;
}

class ErrorBoundary extends Component<
  { children: React.ReactNode; fallback: React.ReactNode },
  { hasError: boolean }
> {
  constructor(props: any) {
    super(props);
    this.state = { hasError: false };
  }

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error: Error, info: React.ErrorInfo) {
    console.error('AI 组件渲染错误:', error, info);
  }

  render() {
    if (this.state.hasError) return this.props.fallback;
    return this.props.children;
  }
}

function validateSyntax(code: string): { ok: boolean; error?: string } {
  try {
    Babel.parse(code, {
      sourceType: 'module',
      plugins: ['jsx', 'typescript'],
    });
    return { ok: true };
  } catch (err: any) {
    return { ok: false, error: err.message };
  }
}

function compileComponent(code: string): React.ComponentType<any> {
  // ⚠️ 生产环境应使用更安全的沙箱方案，这里仅做演示
  const exports: any = {};
  const module = { exports };

  // 简化版：将代码包裹为函数执行
  // 实际生产请使用 iframe 或受控 eval 环境
  const fn = new Function(
    'React',
    'module',
    'exports',
    `${code}\nreturn module.exports.default || module.exports;`
  );

  const Component = fn(React, module, module.exports);
  return Component;
}

export default function SafeComponentRenderer({ code, fallback }: Props) {
  const [syntaxError, setSyntaxError] = useState<string | null>(null);
  const [Component, setComponent] = useState<React.ComponentType<any> | null>(null);

  const renderComponent = useCallback(() => {
    const result = validateSyntax(code);
    if (!result.ok) {
      setSyntaxError(result.error || '语法错误');
      return;
    }
    setSyntaxError(null);
    try {
      const Comp = compileComponent(code);
      setComponent(() => Comp);
    } catch (err: any) {
      setSyntaxError(`编译失败: ${err.message}`);
    }
  }, [code]);

  if (syntaxError) {
    return (
      <div style={{ padding: 16, border: '1px solid #ff4d4f', borderRadius: 8, background: '#fff1f0' }}>
        <h4>⚠️ AI 生成代码未通过校验</h4>
        <pre style={{ whiteSpace: 'pre-wrap' }}>{syntaxError}</pre>
      </div>
    );
  }

  return (
    <div>
      <button onClick={renderComponent} style={{ marginBottom: 12 }}>
        安全渲染 AI 组件
      </button>
      {Component && (
        <ErrorBoundary fallback={fallback || <div>组件运行出错，已降级显示</div>}>
          <Suspense fallback={<div>加载中...</div>}>
            <Component />
          </Suspense>
        </ErrorBoundary>
      )}
    </div>
  );
}
```

### 使用示例

```tsx
import SafeComponentRenderer from './SafeComponentRenderer';

const aiCode = `
export default function AIButton() {
  return <button onClick={() => alert('Hello from AI!')}>点我</button>;
}
`;

function App() {
  return <SafeComponentRenderer code={aiCode} />;
}
```

### 练习建议

1. 将 `compileComponent` 替换为 **iframe 沙箱**实现，使 AI 组件与主应用完全隔离。
2. 为生成的 props 增加 **Zod Schema 校验**，确保 LLM 不会传入未定义的属性。
3. 增加依赖白名单检查：扫描代码中的 `import` 语句，禁止非白名单依赖。

## 思考题

1. **分层防御**：在你的项目中，如果引入 AI 生成组件，你会优先加固哪一层防线？是生成约束、静态校验、运行时隔离，还是人工审核？
2. **Schema 设计**：如果要让 LLM 生成一个「数据表格组件」，你会如何设计输出 Schema，既能保证可靠性，又不限制模型创造力？
3. **安全边界**：`new Function()` 和 `eval` 执行 AI 代码有哪些风险？iframe 沙箱相比它们有什么优势和局限？
4. **版本漂移**：当 React 19 正式发布后，AI 模型可能仍习惯使用旧 API，你会如何设计一个「版本适配层」来平滑过渡？

## 今日小结

AI 生成 React 组件的可靠性不是单一技术点，而是需要从**生成约束 → 静态校验 → 运行时隔离 → 人工回退**构建完整防线。今天的核心收获是：不要信任 LLM 的原始输出，而是让它在受控 Schema 内工作，并通过 Error Boundary 和沙箱机制保护主应用。
